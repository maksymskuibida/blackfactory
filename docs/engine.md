# The engine: `bf`

`bf` is the Black Factory engine. It is one Rust binary. Each command is one short process: no daemon, no network, no background work. It keeps the facts of a project in plain files, and it refuses to move a unit, a checkpoint or a gate forward unless the facts support it.

This page lists every command with one example and the refusals you can meet. For the record kinds and their fields see [records.md](records.md).

## Build and try it

```bash
cargo build --release          # binary at target/release/bf
cargo test                     # unit, attack, resume, timing and end-to-end tests
```

```bash
cd your-git-project            # a git repository with at least one commit
bf init --name myproject       # creates factory/ and .bf/, adds .bf/ to .gitignore
bf status
```

## How the code is cut

The run part is one module per part, in `crates/bf/src/run/` (`brief`, `checkpoint`, `land`, `next`, `pause`, `report`, `roles`, `status`, `sync`, `tokens`, `unit`, `unit_sync`), and the command-line part is one module per command, in `crates/bf/src/cli/` (`amend`, `ask`, `brief`, `checkpoint`, `cost`, `doctor`, `evidence`, `gate`, `guard`, `human_turn`, `init`, `ledger`, `log`, `next`, `plan`, `policy`, `record`, `report`, `review`, `run`, `status`, `unit`, `view` and the rest, each file named for its command). The cut changed no behaviour: a new command or a new part of the run goes into a module of its own, so units that touch different parts do not touch the same file.

## What lives where

| Path | What | In git? |
|---|---|---|
| `factory/config.toml` | project name, main branch, branch prefix | yes |
| `factory/policy.toml` | limits, model tiers, budget cap, review rule, guard settings, the check PATH. Only the human edits it, and a change takes effect only when the human accepts it (see `bf policy`) | yes |
| `factory/records/<ID>.toml` | one record per file | yes |
| `factory/receipts/rc-NNNNN.toml` | receipts written by `bf evidence` | yes |
| `factory/evidence/<sha256>` | files attached to a check, stored by hash | yes |
| `factory/log/events.jsonl` | the append-only run log | yes |
| `factory/checks.json` | a mirror of the project default of the named checks (the log is the truth; `bf doctor` compares them) | yes |
| `.bf/guard.json` | the signed table `bf guard` reads | never |
| `.bf/drafts/`, `.bf/briefs/`, `.bf/work/<ID>/` | drafts, briefs, working copies | never |
| `<state>/<project id>/key` | the key that seals receipts, chains the log and signs the guard table | never, and outside the project tree |
| `<state>/<project id>/head.json` | the log's head: event count, last hash, the main commit the engine last made or the human accepted, the main branch's name, the hash and time of the accepted policy | never, outside the project tree |
| `<state>/<project id>/policy.accepted.toml` | the policy the human accepted: **this** is the policy in force, not the file on disk | never, outside the project tree |
| `<state>/<project id>/tokens.json` | the token of each open worker directive | never, outside the project tree |
| `<state>/<project id>/programs.json` | where each command check's program was found and a hash of that file, recorded when the plan gate is approved; a change is noted in the receipt | never, outside the project tree |
| `<state>/<project id>/guard.gen` | the number of the newest guard table; an older signed table is refused | never, outside the project tree |

`<state>` is `$BF_STATE_HOME`, else `$XDG_STATE_HOME/blackfactory`, else `~/.local/state/blackfactory`. `bf init` creates `<state>/<project id>/` with owner-only permissions (0700; the key is 0600); the project's `factory/config.toml` stores only the id. A fresh clone has no key there, so it cannot verify the log or old receipts: run `bf init`, then the human runs `bf head accept` (see below) and the checks are run again. State is never stored in a database. Everything about a run (which unit is where, which gate is open) is replayed from the log each time, so a killed command leaves nothing half-written that a later command cannot read.

## Workspaces: the factory apart from its code

Two ways to set a project up, one code path. **A project folder** (`bf init` in a git repository) holds the factory and the code together: its one code repository is the folder itself. **A workspace** (`bf init --workspace` in a folder of its own) holds only the factory: `factory/` (records, receipts, the log), `.bf/` (derived files and the working copies) and the harness files. It is normally a private git repository of its own (`bf init --workspace` makes it one if the folder is not one yet), and points at one or more code repositories listed in `factory/workspace.toml`:

```toml
[[repo]]
name = "app"
path = "../app"        # absolute, or relative to the workspace
main_branch = "main"
```

- `bf repo add <name> <path> [--branch B]` adds a repository and notes where its main branch stands; `bf repo list` shows them **The recommended layout is the workspace as the root the human opens, with each code repository a folder inside it** (`./app`, with its own `.git`). The path must be the top of its own git repository with that branch (the branch defaults to the one checked out), not the workspace itself and not inside `factory/`, `.bf/`, `.claude/` or `.git/`; a path beside the workspace (`../app`) works as well. For a repository inside the workspace the engine adds `/<folder>/` to the workspace's **local** ignore file, `.git/info/exclude` (not `.gitignore`), once, and says so; `bf init` and `bf doctor` put the line back when it is missing (a fresh clone of the workspace has no exclude file), and `bf doctor` has a line for it. Nothing of a nested repository is ever staged or committed into the workspace by the engine: it makes no `git add` in the workspace, and content hashes are taken only of working copies. A project folder has exactly one repository, named `code`, at `.`.
- All `bf` commands run from the workspace, from inside a working copy, or from inside a nested code repository: a command finds its project by walking up to the folder that holds `factory/`. **A workspace above wins** over any nearer folder, so a code repository that itself contains a folder named `factory/` (even one with a `config.toml`) is never taken for the project, whether the command runs from its checkout or from a working copy of it. Inside a workspace's working copies the guard treats that `factory/` folder, and `.claude/`, as the repository's own content (a worker may change them within its unit's `files`); only `.git` is off limits there. The workspace's own `factory/` stays protected.
- A **unit** names the repository it changes with `repo = "<name>"` (the only repository is the default; with several, `bf plan check` refuses a unit that names none or an unknown one). Its `files` are relative to that repository, and two units in one wave clash only when they touch the same path of the same repository.
- A unit's working copy is a git worktree of its repository, at `.bf/work/<U>` in the workspace, on branch `bf/<U>`. **Checkpoint branches live in each repository the checkpoint's units change**: a checkpoint over one repository has its working copy at `.bf/work/<K>`; over several it is a folder `.bf/work/<K>/` with one working copy per repository in `.bf/work/<K>/<repo>/`, and its checks run from that folder. Landing merges inside the unit's repository. Closing a checkpoint closes it in each repository, and a merge (with the human's go-ahead, as ever) merges the checkpoint branch onto the main branch of each, whose main checkout must be on it.
- The content a receipt is bound to is the content of the unit's or checkpoint's working copy (for several repositories, a hash of the working copies' hashes by repository name). In a workspace nothing is left out of the hash; in a project folder `factory/` and `.bf/` are.
- The **main-branch note is kept per repository**: the log head records, for each repository, the branch watched and the commit the engine last put there or the human accepted; `bf status` lists the repositories (`repos`) with where each stands, and its `main` is all of them together. `bf head accept` takes every repository as it stands, under the branch names the files give.
- Code repositories get **nothing written into them** except branches, worktrees and the commits workers and landing make: no `factory/`, no harness, no ignore entries. The check sandbox also denies a check writing to their `.git/hooks` and `.git/config`.
- The guard's root is the workspace: `factory/`, the harness files and the guard table are protected there as before. A worker may write only inside its own working copy, within its unit's files; a write by a worker into a code repository's own checkout is denied. Nobody writes git hooks or git config of a code repository through the Write tool; the human edits the checkouts freely.
- Not covered: records that are not in git at all, and one unit changing two repositories.

## The run log

One JSON object per line. Each event has `seq`, `at`, `kind`, its data, `prev` (the hash of the event before) and `h` (its own hash). `h` is an HMAC-SHA256 under the project's key, which lives outside the project tree: a line written by hand, with a correct `seq` and `prev` and a plain hash, does not verify. Editing or deleting a past line breaks the chain. A line cut short by a killed process is ignored and removed by the next write.

**The head.** The state folder also holds the log's head: how many events there are and the hash of the last, written under the same lock as every append. Every command that reads or changes state compares the log with it. A log that is **shorter** than the head, or whose event at that place **differs**, was rolled back (an old copy put back, `git stash`, a checkout, a restore) and is refused with the reason and a recipe that never says "restore from git". A log that is longer is accepted when the extra lines verify (a command was killed between the append and the head).

**Recovery: `bf head accept --quote "<the human's words>"`.** Only the human decides to keep a log that does not verify or does not match the head. After they say so in chat, this command chains the whole log again under the current key, sets the head to its end and appends a `head.accept` event naming what was wrong. It needs an unused human turn and a quote, like an approval. It also accepts where the main branch stands now (see `bf checkpoint close`), and it is the way to take a cloned project under a new key (old receipts must then be run again). `bf doctor` and `bf log --verify` still work on a damaged log.

## The policy

The policy in force is the copy the human accepted, kept in the state folder with its hash in the log head; the file `factory/policy.toml` is where the human edits. `bf init` accepts the policy that is there the first time. After that, **every command refuses while the file on disk says something different from the accepted copy** (a comment, blank line or reordering that leaves the parsed policy equal is not a difference), with the reason and a recipe: the human reads the change with `bf policy diff` (lines removed and added), and if they agree they say so in chat and `bf policy accept --quote "<their words>"` takes it (a decision like an approval, logged as `policy.accept`). Running `bf init` again does not accept a changed policy. The guard table, the role-token setting, the approval words, the check PATH, the transcript root and every other setting are read from the accepted copy only, so an edit of the file switches nothing on or off by itself. `bf doctor` and `bf log` still run while the policy is unaccepted.

## Common behaviour

- Exit codes: `0` done, `2` refused, `1` error.
- `--json` prints data as JSON. A refusal under `--json` is printed to stdout as `{"ok": false, "refused", "because", "do_this", "it_worked_when"}`.
- Every refusal has four parts, printed in this order on stderr: `refused:` what was refused, `because:` why, `do this:` numbered steps, `it worked when:` how to tell.
- `-C <dir>` runs the command as if started in `<dir>`.
- From inside a unit's working copy, `bf` finds the project's main checkout by itself. State always lives in the main checkout.
- Every command that changes state rewrites `.bf/guard.json`.

## Commands

### `bf init [--name N] [--workspace]`

Creates `factory/`, `.bf/`, a default policy and config, the sealing key, and the guard table, and adds `.bf/` to `.gitignore`. `--workspace` makes a workspace (see above): it needs no git repository to start from (it creates one) and adds `factory/workspace.toml`, which `bf repo add` fills. Safe to run again: it only refreshes the key, the guard table and the ignore line.

```bash
bf init --name myproject
```

Refuses when: the folder is not the top of a git repository (not for `--workspace`).

### `bf record put <kind> --file <f>` / `get <id>` / `list [--kind k]`

`put` validates a TOML (or `.json`) file against the schema of its kind and writes `factory/records/<ID>.toml`. A file without `id` gets the next free one. `get` prints a record, `list` prints `ID title` lines.

```bash
bf record put requirement --file r1.toml
bf record get R-1
bf record list --kind unit
```

Refuses when: the record does not match its schema (every problem is listed); the `id` is taken by a different record and `--replace` was not given; the kind is unknown; the file cannot be read; the record's stage gate is approved and the content changes without an approved amendment.

### `bf id new <kind>`

Prints the next free ID of that kind, for example `R-8`, and reserves it: the next `id new`, and a `put` of a file with no `id`, hand out a later number. Numbers may have gaps. To use a reserved ID, write it into the file's `id` field.

**The ID rule for `bf record put`.** It never renumbers silently. (1) A file with no `id` gets the next free ID, and the command says so in plain words (`put R-9 (the file had no id, so the engine assigned R-9 ...)`; `"assigned": true` in JSON). (2) A file whose `id` belongs to a *different* record is refused with the way out: put a fresh ID (`bf id new`), or run the same command with `--replace` to revise that record on purpose. (3) The same content again is accepted and changes nothing. (4) Findings are the exception: a reviewer replaces one by putting it again (to set its `outcome`). (5) **Frozen stages.** Once a stage's gate is approved, a changed record and also a **new** record of that stage's kinds (a unit, handoff, check or checkpoint after the plan gate; a requirement after the requirements gate; and so on) is refused unless an approved amendment names it. `bf unit start`, `bf unit land`, `bf checkpoint close` and `bf doctor` also compare the records with what the gate approved (its snapshot) and refuse on drift, so a record edited or added by other means is found. (6) IDs have no leading zeros (`R-007` is refused). (7) Allocation and writing happen under a lock, so parallel puts never share an ID.

### `bf ledger check [--plan]` / `bf ledger impact <ID>...`

`check` lists every designed part that has no unit, no check or no evidence, and refuses while any exists. `--plan` checks only units and checks (use it before building). The designed kinds are set in `factory/policy.toml` under `[ledger] kinds`. Evidence means a sealed, passing receipt from a check of a **closed** checkpoint that proves the part, at the content that checkpoint closed on (a receipt from a version that no longer exists counts for nothing); for a human check, the checkpoint's approved step gate.

A **handoff is a row too**: it needs a proving check, and evidence, which is a passing receipt of that check at the content its unit landed on (a unit check) or its checkpoint closed on (a checkpoint check).

`impact` prints everything linked to the IDs: units that deliver them and units that depend on those, handoffs, checks, checkpoints and receipts.

```bash
bf ledger check
bf ledger impact R-1 C-2 --json
```

Refuses when: any designed part lacks a link (a threat is a designed part, so each needs a check that proves its answer); a required named check has no proof (a design-stage product missing, or a built-stage check with no passing receipt at the content of the last checkpoint); a marked legal finding is not acknowledged.

### `bf plan check`

Checks the delivery plan: every handoff is proved by some check (a check's `proves` may name a handoff `H-n`; so may a checkpoint's), and at least one such check really runs, that is, belongs to a unit (`unit = "U-n"`) or is listed in a checkpoint's `checks`; no cycle in the unit graph; every handoff has a sender, a receiver (which depends on the sender) and a named thing; every checkpoint names the IDs it proves and a check for each; every designed ID belongs to a unit and to a checkpoint; every unit has a check; units in one wave share no files. Waves are the levels of the dependency graph.

Refuses when: any of that fails (all problems are listed). It also refuses while the check settings are undecided (the human has recorded neither the project default nor the settings of a run: decide the default with `bf checks propose --scope default` and `bf checks set --quote` first), while a required named check has no check record with `named = "<name>"` (a design-stage threat model and markets statement need none), while such a record's `how` is not the way the catalogue says it is proven, while a required built-stage check is not listed by the last checkpoint, and while a named check record belongs to no unit and is listed by no checkpoint.

### `bf run start` / `bf run stop` / `bf status` / `bf log`

`run start` begins a run (it needs a plan that passes `plan check`). `run stop` ends it. `status` prints the project, the run, test mode, every unit's state (`planned`, `ready`, `running`, `review`, `fixing`, `reviewed`, `blocked`, `parked`, `landed`) and every gate. `log` prints events: `--tail N` for the last N, `--verify` to check the hash chain.

`status` also prints `main`: whether the main branch is where the engine left it (see `bf checkpoint close`), with one quiet line when a person committed on it, and `bad_records`: record files that cannot be read, each named with the reason. One unreadable record file never stops `status`; `bf plan check` and `bf doctor` report it as a problem, and a command that asks for that record by id names the file.

Refuses when: a run is already active; the plan has problems; the log chain is broken. **`run stop` is refused** while a required named check has no proof (the same test as `bf ledger check`, plus a marked legal finding that is not acknowledged), unless the human switched that check off for the run; the refusal names each gap and the way out (`bf checks propose --scope run <check>=off:<why>`, then `bf checks set --quote`).

### `bf next`

The next directives as data: for each, `role` (`builder`, `reviewer`, `verifier`, `engine`, `human`), `action`, the `unit` or `checkpoint`, `tier` (`cheap`, `standard` or `strong`, from the policy), `working_copy`, `brief` (the path `bf brief` will write), `limits` and the `commands` to run. Engine steps have `role: "engine"` (`land`, `close-checkpoint`) and a single `command`; worker directives carry a list of `commands` and the verifier's directive for a checkpoint has `brief` and `limits` like the others; human steps have `role: "human"` (`open-gate`, `decide-gate`, `decide-unit`). Before the plan gate is approved the only directive is the design gate to deal with: **the first design gate, in order (idea, requirements, ui, architecture, plan), that is neither approved nor skipped**. If it is open, the directive is for the human to decide it (`decide-gate`, with the gate ID). If it is not open and would open, the directive is `open-gate` with its command. If opening would be refused for want of records, the directive is for the conductor (`role: "conductor"`, `action: "add-records"`, with `missing` saying what: the idea file, a requirement, a screen or journey, a component and a decision, a plan that passes the check); for the ui gate it also carries `skip_command`, because a product with no interface skips the gate instead (`bf gate skip ui`). A directive never carries a command the engine would refuse, and a later gate is never offered while an earlier one waits. (With `[gates] in_order = false` the plan gate is offered as before.) `waiting` says why other units are not ready.

It also says plainly whether anything can start: `can_start` (a worker or engine step exists), `human_needed`, and `idle_reason`, which is null when something can start and otherwise says why not: `run done: ...`, `units parked or blocked: U-3 (parked); the human decides`, `waiting on a human step`, or `nothing is ready: ...`.

```bash
bf next --json
```

`bf next` also runs the idle check (see `bf stuck`) before it answers, so nobody has to call it. Questions that workers put to the human appear as `human` directives (`answer-question`) and hold only their own unit (see `bf ask`).

**When the human's messages are not being recorded**, the factory says so early, as information and never as a refusal: when the log holds events of a conductor at work and not one `human.turn` or `human.turn.rejected` since the project started, `bf status` prints a `note:` line (JSON: `human_turns_note`), `bf doctor` has a `human turns` line, `bf ask` and `bf next` print the same line on stderr (`bf next --json` carries `human_turns_note` too), and a gate decision with no human turn points at the same cause first. The usual cause is that Claude Code was started in a folder other than the one that holds `factory/` and `.claude/settings.json` (for a workspace, the workspace folder itself), so the hook never loaded.

Refuses when: no run is active; the budget cap is reached.

### `bf brief <unit-or-checkpoint> --role <builder|reviewer|verifier>`

Given a checkpoint ID (`K-1`), it writes the verifier's brief for the checkpoint: what it proves with acceptance, its checks with the exact commands, no source scope; other roles are refused for a checkpoint. Given a unit, it writes the exact context for that worker to `.bf/briefs/<unit>-<role>.md` and prints the path: the unit, the design parts it delivers with their acceptance, the contracts it receives and hands over, its checks with the exact command, its file scope, open findings, limits and rules. A reviewer's brief also lists the unit's receipts. A verifier's brief leaves out the file scope and tells it not to read the source.

**The engine writes the briefs itself.** `bf unit start <U>` writes the builder's brief, the same file `bf brief <U> --role builder` writes, also when it resumes a unit already in flight. When a builder's report moves a unit into review (`built` or `fixed`, so also each round after a fix), the engine writes the reviewer's brief. When a reviewer's report sends a unit back to fixing, it writes the builder's brief again, with that round's findings. A reviewer's report of findings or of a clean review on a unit in review is **refused while the reviewer's brief file is missing**; the refusal names `bf brief <U> --role reviewer` and changes nothing. When the engine cannot write a brief, the command that moved the unit still succeeds, says so (`brief_note`) and leaves no older brief of that role in place. `bf next` still lists `bf brief` in its directives, as a refresh: the conductor's and the reviewer's instructions say so, and running it again writes the same file from the state as it is now.

### `bf report <unit> --result <built|findings|fixed|blocked> --token T [--role R] [--note T] [--findings f] [--cost N]`

The only way a worker changes a unit's state.

**Role tokens.** With `[roles] tokens = true` (the default), `bf report` needs the token of the directive it reports on: the builder's token for `built`, `fixed` and `blocked`, the reviewer's for the review. The token only says which role is reporting. `bf next` shows the current token in every builder and reviewer directive (`token`), **every time it is asked**, until a report spends it: a conductor that resumes, or a new one, always has the token of the work already handed out, and nothing needs the human to reset it. Tokens of directives that no longer exist are dropped. A builder cannot report as the reviewer: the reviewer's directive exists only while the unit is in review, and `bf next` and `bf brief` refuse to run from inside a working copy. **Cost.** With a budget cap, every report must carry `--cost <number>` (the conductor reads the session's real usage); text that is not a number is refused, never counted as zero.

| Unit is | Report | Becomes |
|---|---|---|
| `running` | `built` | `review` (or `reviewed` if the policy does not require review) |
| `review` | `findings --role reviewer [--findings f.json]` | `fixing` while a finding is open (new ones from the file, or filed with `bf record put finding`); `parked` after more than `max_rounds` rounds; `reviewed` when there is no finding at all |
| `review` | `built --role reviewer` | `reviewed` (refused while findings are open) |
| `fixing` | `fixed` (or `built`) | `review` |
| `running`, `fixing` | `blocked` | `blocked` (counts as an attempt) |

`--findings -` reads the list from standard input, so a reviewer needs no file. A findings file is a JSON list such as `[{"title": "...", "severity": "high", "where": "src/a.rs:10", "action": "..."}]`; each entry becomes a finding record with an ID that never changes. `--cost` adds to the budget count.

A finding is open until its `outcome` is `fixed` or `accepted`. A reviewer can file one from the unit's working copy with `bf record put finding --file f.toml`; the auditors (`security-auditor`, `legal-auditor`) can file findings only while a unit is in review, until a later unit changes that. Only a new, open finding can be filed, for a unit that is in review (workers may put nothing else, and may not mark a finding fixed or accepted); the human sets `outcome = "accepted"` by putting it from the main checkout.

Refuses when: no run is active; the report does not fit the unit's state; a unit in review is reported on without `--role reviewer`; a clean review is reported while findings are open; a reviewer reports on a unit whose reviewer's brief file is missing (see `bf brief`).

### `bf unit start <U>` / `bf unit land <U>` / `bf unit release <U> --quote "..."`

`start` creates the unit's working copy (on a unit that is already in flight it only makes sure the working copy exists) at `.bf/work/<U>` on branch `bf/<U>`, cut from the local branch of its checkpoint (`bf/<K>`). **A checkpoint's branch is cut from the branch of the checkpoint just before it in plan order** (the first from the main branch), so each checkpoint holds everything before it and the last one holds the whole result; the first unit of a checkpoint therefore waits until the earlier checkpoint is closed (`bf next` says `builds on K-1, which is not closed yet`). If work lands in an earlier checkpoint after a later branch was cut (an amendment re-opened it), it is merged into the later branch before more lands there. It needs an active run, an approved plan gate, and the unit's dependencies and handoffs satisfied. Running it again resumes the same working copy. It also writes the builder's brief (see `bf brief`).

`land` merges the unit's branch into its checkpoint branch (no network). It re-checks first: the unit is `reviewed`; no finding is open; every check of the unit has a sealed passing receipt for the content now in the working copy; every changed path is inside the unit's file scope. Pending changes are committed in the unit's working copy first. **A unit lands only on the content its last clean review judged**: when the unit's last review round is clean, records the content it judged, and that content differs from the content now in the working copy, landing is refused and the unit goes back to review (a `unit.report` event from the engine), the refusal says so and names the reviewer's next round as the way on, and after a clean report on the new content the unit lands. A unit whose last clean round judged the current content, a run that does not require review, and a log whose rounds carry no content land as before.

`release` is the human's way back for a unit that is `parked` (after `max_rounds` review rounds, `max_attempts` failing check runs or blocked reports in a row, or an idle limit) or `blocked`. It needs the human's words as a quote, like an approval. The unit goes back to work (`fixing` if it was parked after a review round, otherwise where it was), its round and attempt counts start again, and the log keeps the history. `bf next` then offers it again.

**Files beyond the list (`bf unit scope`).** A unit may change only the files its record lists. A builder that needs one more file, most often a test its own change breaks, asks: `bf report <U> --result blocked --token T --need-files -` with a JSON list on stdin, one object for each single file with `path`, `why` (the acceptance item or record the change serves) and `patch` (a unified diff against its working copy for a file that exists, a few lines describing a new one). The report counts as an attempt like any blocked report, and the unit stays `running` or `fixing`. A folder, a pattern or an existing file without a patch is refused, naming the file and the rule, for the builder to correct.

Never granted, by anyone, and refused before any review, so the unit goes to `blocked` for the human as a plan repair (except the last case, see below): a place the guard protects (the factory's records, the policy, the run's state, the hook settings, the git folders, the installed skill and panel, the policy's extra protected paths); a file outside the code repository of the unit; and a file that another unit of the same checkpoint holds in its list or its grants when that unit has not landed and does not depend on this unit, directly or through others. The last rule is checked again when the verdict comes. A file held that way no longer blocks the unit for the human: the unit waits and goes on by itself (A-73, below); the other cases stay a plan repair.

While a valid request is open, `bf next` gives a `review-scope` directive instead of the builder's: role reviewer, the policy's reviewer tier, a one-use token, and a brief from `bf brief <U> --role reviewer` with the unit's parts and acceptance, its text, its file list and earlier grants, the changes in its working copy against its checkpoint branch, the request and the question. The question, for each file: is it needed for the unit's original scope (a file of any kind without which the behaviour the unit's records describe cannot be built, tested or documented: an existing test the unit's change breaks, a new test of its behaviour, a doc its behaviour makes untrue, a file the unit's text names that its list missed, a source file the behaviour must be wired into or split out to), or a scope extension (new behaviour no record of the unit describes, a different feature, work the records give to another unit)? A test the unit breaks or adds is never an extension. The reviewer answers once: `bf report <U> --role reviewer --result scope --verdict - --token T` with a JSON list of `{path, verdict: needed|extension|retry, why, must}` (`must` for a `retry` only), every requested file once. A builder's token is refused.

Each file marked needed is granted at once, with no amendment, approval or release: the log gets a `unit.scope.grant` event with its number for the unit, the files, the reasons, the patches and the marks, the guard's table is rewritten, and the builder gets a new directive and token with its round and attempt counts unchanged. A file marked extension is not granted: the unit goes to `blocked` for the human with the reasons, and the needed files of the same request are granted beside it (a late hard rule is treated the same way). A file marked `retry` is not granted either, and with no `extension` and no late hard rule in the same request it holds back the whole request, so none of the needed files is granted beside a `retry`; when the same request also has an `extension` or a late hard rule, the unit goes to the human and the needed files are granted. The reviewer gives `retry` with `must`, the words a corrected patch must meet, and the builder asks for the same file again with a corrected patch, which the reviewer judges. A file is judged at most as many times as the policy's review rounds (`max_rounds`) for one unit, counted from its latest start or release; a `retry` in the last round is written `retry_spent`, and an `extension` goes to the human, who is also asked when the rounds run out. A request for a file whose rounds are spent, or with the patch already judged, is refused naming the file. A checkpoint fix is asked the same three ways, with its rounds counted for that fix only: for a checkpoint fix, none of the needed files is granted beside a `retry` or an `extension`; the request is answered by one refusal that lists every file with its verdict, and the builder asks again for the needed files with their patch as it was. The fix goes back to work, and for an `extension` or a spent `retry` the way on is a gap report that names the files, which goes to the human. The unit's record never changes: wherever the engine reads a unit's files (the guard's table, the briefs, the check at landing, a checkpoint fix's file set and its attribution to units) it reads the record's list plus the grants. `scope_review = false` in the `[review]` section of the policy sends every request to the human as before.

A grant is marked for the checkpoint reviewer when it holds an instruction file of the harness that the unit's own list does not hold (`harness/`), build, test-runner, lint or CI configuration (manifests, lock files, `build.rs`, `.config/`, `.github/`, the rustfmt and clippy settings), a new source file the unit's text does not name (`new source file`), or an existing source file granted after three others (`source file after three`). Marked grants are tagged Look first on the run page and the checkpoint page, and listed first in the checkpoint review's brief. The unit reviewer's brief lists the grants with their patches and marks. `bf status --json` shows for each unit `scope_request` and `scope_grants`, and `waiting_for` names a scope review while one is open. Landing also refuses a unit whose changes remove a line of a granted existing test file or configuration file that the patch does not remove, naming the file and the line.

`bf unit scope <U> --revert <n> --quote "..."` is the human's withdrawal of grant `n` before the unit lands. The files leave the scope, the log keeps both events, and when the unit's branch already changes them the unit goes to `fixing` with a note in its brief to undo those changes. After landing it is refused: raise a finding at the checkpoint review, or an amendment.

**Bookkeeping stops go on without the human (A-73).** A unit stopped by bookkeeping is not a gap in the design, so the engine and the conductor carry it on, each step an event in the run log with its cause; a log written before these steps replays to the same state as before. Rounds and attempts are kept by every step below, and only the human's release resets them; a hard refusal and a blocked report each count as an attempt, so a unit that keeps asking or keeps blocking parks at the attempt limit.

- **An approved amendment puts blocked units back to work.** Approving an amendment returns every blocked unit it re-opens, and every blocked unit whose check record it changes, to the state it was blocked from, with no `unit.release` event. A parked unit stays parked.
- **Waiting for a held file.** A request for files refused only because units beside it hold them no longer blocks the unit for the human: the unit is `waiting`, `bf next` asks nothing of the human for it and lists it with its holders (`wait_for`). When every one of those files is free (its holder landed, or an approved amendment put the holder after the unit), the engine puts the unit back to work by itself, and its next directive names the files to ask for again.
- **The engine's order for a holder that has not started.** When the holder of a requested file has not started, is in the same checkpoint, and putting it after the asker makes no cycle, the engine puts it after the asker in the run log (no record changes) and the request goes to the scope reviewer as usual.
- **The builder reconsiders.** A builder's plain blocked report is followed by one more builder directive, the reconsider directive: its brief shows the report's note and the ways on (ask for the file, put a stray change back, name format-only files, or report built). A plain blocked report made from that directive goes to the human.
- **Still the human's:** a park at the round or attempt limit, a scope reviewer's extension verdict, a file in a place the guard protects, in another repository or behind a link, a plain block the builder confirms after looking again, and every amendment.

### `bf unit pause <U>` / `bf unit resume <U>`

The conductor's, from the project folder, with no quote and no token. A pause is taken for a running, review or fixing unit (to keep within the human's cap of units in flight), a resume for a paused one. A paused unit gets no worker directive from `bf next` and is listed as waiting with the command that resumes it. `bf stuck` never parks a paused unit, a unit with an open question asked for it, or a unit named by an open amendment, and the idle clock starts again at the resume or at the answer. A pause changes no round, attempt or limit.

### `bf unit restore <U> <path>... --token T`

The builder's, from its working copy. It puts each named file outside the unit's files and grants back to its content at the base the landing diff uses, or removes it when the base has no such file, and records the restore in the run log. The unit's state, rounds and attempts do not change.

### `bf unit format <U> <path>...`

The conductor's, before the reviewer starts, for files a builder's report names as format only. For each file the engine runs the formatter on the file's content at the base the landing diff uses, with the formatter settings and the edition of that base (in this version Rust source files, with rustfmt), and accepts the file into the unit's scope only when the result is byte for byte the file in the working copy. It records a grant marked format only, with the base, the hashes and the formatter, and asks no one. It refuses, naming each file and the reason and recording nothing, when a named file changes more than formatting, has no formatter the engine knows, is new, deleted, inside the unit's files, in a place the guard protects, behind a link or held by a unit beside it, or when the formatter cannot be found or fails. Landing is the check that follows: it refuses a unit whose format-only file differs from the content accepted, or whose base changed since, naming the file. The grant is shown to the unit reviewer, the checkpoint reviewer and the human with its mark, and the human may withdraw it like any grant.

### `bf unit sync <U>`

The conductor's, with no token, quote or counter reset, for a unit whose branch is behind its checkpoint branch (`bf status` shows it). It is a fast-forward when the unit has no commits of its own and a merge otherwise. It is refused, leaving the working copy exactly as it was, on a conflict, a dirty working copy or a unit in review. `bf unit start` and `bf unit release` fast-forward a clean unit with no commits of its own by themselves. Each sync is a `unit.sync` event with its cause and both bases. It is safe because landing takes the unit's changes from the merge base, so the checkpoint's files merged in never count as the unit's changes, and receipts sealed before the sync are stale, so the checks run again on the merged content.

```bash
bf unit start U-1
bf unit land U-1
```

Refuses when: the plan gate is not approved; the unit is not ready or not reviewed; a receipt is missing, unsealed or for other content; the branch changes files outside the scope; the merge conflicts (the merge is aborted).

### `bf evidence run <check> [--unit U] -- <command...>`

Runs the command itself, in the current working copy, with output and errors merged. It stores a bounded tail of the output (4000 bytes by default), the SHA-256 of the full output, the exit code and the content hash (see below), and writes a sealed receipt.

```bash
cd .bf/work/U-1
bf evidence run X-1 --unit U-1 -- cargo test
```

A check's command is one program and its arguments, started through `/bin/sh -c` with every word quoted: each word reaches the program as an argument as it is, and no operator acts (a word that is an operator is refused beforehand, as below). The engine refuses a command that holds a shell operator or redirection as a word (`&&`, `||`, `;`, `|`, `&`, `>`, `>>`, `<`, `2>&1` and the like) or, written as one string, a quote, a backtick, a backslash or `$(`. `bf plan check`, `bf evidence run`, the proposals of `bf checks unit` and `bf checks wave` and a checkpoint reviewer's probe all refuse it, naming the check and the word. The two ways out are one check per program, or the list form (`command = [...]`) for an argument with a space. The command runs with an environment of its own: nothing is taken from the caller except a short list (`HOME`, `USER`, `LANG`, `TMPDIR`, `CARGO_HOME`, ...), and `PATH` is the one in the policy's `[exec] path` (captured at `bf init`, editable by the human only). A fake program first on the caller's `PATH` cannot stand in for the real one. Every git call the engine makes also runs without the caller's `GIT_*` variables, with the policy's `git` program and no user or system git config, so `GIT_DIR` or `GIT_WORK_TREE` cannot point the content hash at another repository. **On macOS every check, and every git call, runs under `/usr/bin/sandbox-exec`** with a profile that denies the network, reading or writing the project's state folder, writing under `factory/` and under the main checkout's `.bf/` outside the working copy in use. The engine tests at start whether `sandbox-exec` works; where it does not (other systems, or a refusal) the check runs **without** a sandbox and the receipt says `sandbox = "none"`, as does `bf doctor`. `[exec] sandbox = false` in the accepted policy switches it off. On the test machine the sandbox adds about 80 ms to one `bf evidence run`. `[exec] network = true` in the accepted policy lets checks reach the network under the sandbox, and `[exec] env = ["JAVA_HOME"]` names more environment variables a check may see. The profile also denies a check writing to `.git/hooks`, `.git/config`, `.claude/` and the transcripts, because git or the harness would run what is planted there later, outside the sandbox. **The folders on the check PATH are not checked for change**: a version manager rehashing its shims or an install changing a folder stops nothing. `bf doctor` lists, for information, the PATH folders that lie inside the project or in the user's home folder. **The program a check starts is recorded when the plan gate is approved**: for each command check, where its first word is found on the check PATH (the resolved path) and a hash of that file, kept in the state folder. Before the check runs the program is looked up again; if it is found somewhere else, or the file's contents differ, the check still runs, `bf` prints a note, and the receipt carries a `program_note`; the new state becomes the recorded one, so a change is noted once. A check added after the plan gate is recorded the first time it runs. Only the first word of the command is covered, not a program that program starts. The receipt records the program that was started (`/bin/sh`), whether it ran in the sandbox, and the hash of the check record it was made for; if the check record changes later, the receipt stops counting.

The command must equal the `command` stored in the check record. Otherwise an agent could run `true` under the name of a real check. The exit code of `bf` is 1 when the command failed (the failing receipt is still stored). Nobody writes a receipt by hand: a receipt without a valid seal is ignored everywhere.

Refuses when: no command is given; the ID is not a check, or the check is not a command check; the command differs from the check's own; the command changed the working copy while it ran (the receipt would describe neither state).

### `bf evidence attach <check> <file> [--outcome met|failed|unreachable --says "..." --token T]` / `bf evidence verify [--unit U] [--checkpoint K]`

`attach` stores a file by hash under `factory/evidence/` and writes a sealed receipt bound to the content. **A check judged by an agent is settled by a stated outcome, not by a file.** `--outcome met|failed|unreachable` with `--says "<one sentence: what was looked at>"` records the judgment; it is accepted only with the verifier's role token (`--token`, the `token` on the verifier's directive from `bf next`; for a check that belongs to one unit, the reviewer's token for that unit). A builder holds neither, so it cannot settle a check for its own unit; with `[roles] tokens = false` no token is asked. `met` is a passing receipt; `failed` and `unreachable` are the marks `bf evidence fail|unreachable` make (the checkpoint waits for the human, and a later `met` at the same content replaces them; while a mark stands, the `decide-check` directive carries `verifier_token` so the verifier can look again). A file attached **without** an outcome is kept as supporting material and settles nothing. The outcome, the sentence and the file are shown on the checkpoint page and the coverage page. A `human` check is settled only by the checkpoint's approved `checkpoint-step` gate, never by a file; a `command` check only by running its command. The size limit is in the policy. The path is resolved when the file is read, links included, and a path that leads into the project's state folder is refused. The same holds for every file the engine reads for a caller (`--file`, `--findings`, `--template`).

`verify` checks the receipts: the seal and the exit code of each, and, with `--unit` or `--checkpoint`, that every check in scope has a sealed passing receipt at the content now in that working copy. Older receipts for other content are listed as `OTHER` and do not fail the command when a current one exists. It exits 2 when anything fails.

**`verify --unit <U>` holds the reviewer to what landing requires.** It lists and requires the same checks `bf unit land <U>` requires, taken from one function: the unit's own check records and the checks every unit must pass, each at the current content and, for the latter, with the same command (a line `NOT MET <check>: ...` names each gap, and the JSON has `unmet`). It also marks each check in scope whose counting pass at the current content followed a sealed failing run of that check at the same content, naming both receipts: a line `PASS-AFTER-FAIL <check> failing <receipt> passing <receipt>` in the text and `pass_after_failure` in the JSON. The mark does not change the exit code: it says that no one judged the failure, and the unit reviewer files a finding for it or says in its closing sentence why the failure is harmless, from the failing receipt's output. Permanent tests hold each case.

### `bf evidence fail|unreachable <check> --reason "..."`

The verifier's way to say that a check ran and does not match (`fail`), or could not be run (`unreachable`), when there is no passing receipt to show. It writes a sealed record bound to the content, in the working copy where it is run. It is never proof. A checkpoint whose check carries such a mark does not close (the refusal names the check and the reason); `bf next` shows a human directive `decide-check` (so `can_start` is false and `idle_reason` says a check failed or is unreachable); the checkpoint view marks the row and sets `needs_you`. A later passing receipt of the same check at the same content replaces the mark, so once the cause is fixed the verifier just runs the check again.

### `bf checkpoint close <K> [--merge]`

Closes a checkpoint (the records must match what the gates approved). All its units must have landed, its working copy must be clean, and every ID in its `proves` list needs a sealed passing receipt, from one of its listed checks, at the content now in the checkpoint's working copy, or an ID waived by an approved amendment. A checkpoint with a `human_step` also needs an approved `checkpoint-step` gate for it.

`--merge` also merges the checkpoint branch onto the main branch (the main checkout must be on it). It needs a human act **after the closure**: the checkpoint must be closed, and an approved `checkpoint-step` gate for it (real, not simulated) must have been opened after the close event (`bf gate open checkpoint-step --ref K`, the human says merge in chat, `bf gate approve <gate> --quote ...`). Merging twice does nothing the second time. A test run refuses it before anything else. After a merge the engine remembers the main commit it made. **The main branch is compared with the commit recorded in the log head**, and the branch watched is the name recorded there too (so an edit of `factory/config.toml` cannot move the watch; `bf doctor` shows the difference, and `bf head accept` takes the config's name). A watched branch that no longer exists is a problem, not "ok".

The recorded commit is set at `bf init`, after an engine merge, and when the human accepts. Ordinary commits by a person, including the first commits of a new project, are not a problem: `bf status` shows one quiet line (`the main branch has moved on ... by commits the engine did not make (3 new); they hold no unlanded or test-run work`) and nothing is refused. The watch complains only about **work that should not be on main**: the commits of a unit that never landed, or that landed in a test run, found on the main branch. Then `bf status` says so (`main.ok` false, with the commits' files), and `bf unit land`, `bf checkpoint close` and `bf ledger check` refuse until the human moves the branch back and, if the position changed, accepts it with `bf head accept --quote "<their words>"`. A run that contains a simulated approval, or a unit landed in a test run, can never be merged.

```bash
cd .bf/work/K-1
bf evidence run X-3 -- cargo test --all
cd ../..
bf checkpoint close K-1
```

Refuses when: units have not landed; the working copy has uncommitted changes; an ID has no proof; a required built-stage named check has no passing receipt at this content (on the last checkpoint, also when it is not listed by it, and when any required check of the run lacks its proof), or a marked legal finding is not acknowledged; a human step is not approved; with `--merge`, the run is tainted by simulated approvals or the main checkout is on another branch.

### `bf checkpoint sync <K> --quote "<the human's words>" [--resolved]`

The run builds on a stack of checkpoint branches cut from the main branch as it stood. When the human merges other work into the repository's **local** main branch meanwhile, the stack and the main branch meet only at the final merge, where they can conflict and where the receipts prove content from before the join. `bf status` therefore says when the main branch holds commits the stack lacks (`main_ahead` in `--json`: repository, checkpoint, commits, the command; plain status prints a `note:` line) and `bf next --json` carries the same as information, never as a directive. `sync` is the supported step: a human act (the same rule as an approval: an unused human turn after the request, the quote in it) that merges the repository's local main branch into checkpoint branch `K`, in each repository of a workspace that `K` touches and whose main branch has commits `K` lacks. The engine makes no network call: pulling from a remote into the local main branch is an ordinary git command done before.

It is allowed only at a quiet point: `K` is open and at the tip of the stack (no later checkpoint has started), and no unit is between start and landing (running, in review, fixing, reviewed, blocked or parked); otherwise it refuses and names the units to finish or release first. It is also refused while a checkpoint fix is open, parked or not, naming `bf checkpoint fix <K> --abort` and `bf next`, because the fix's abort would put the checkpoint back to before the sync. Nothing to take in is not an error: it says so and changes nothing. **The joined content is proven before a sync counts, conflict or not.** After the merge (automatic, or resolved through `resolve-sync`) the engine runs the sync's checks on the joined content. **The sync's checks are the command checks every unit of the checkpoint is held to, each distinct command once, whether they come from unit check records or from the list of checks every unit must pass (for a project whose list is the default suite and the lint step, those two, so a sync runs no timing test).** A checkpoint whose units share no command is synced with the checkpoint's own command checks, as before. The engine runs them when it starts, when the resolver reports and when the human records the merge as resolved; it does not run the checkpoint's own checks in a sync, because those run only at verification. Each run is recorded in the evidence (`bf evidence verify --checkpoint <K>` lists them apart, as `sync:<check>` rows) with its command, exit and content, and settles nothing: no unit's check and no checkpoint's check counts it (agent-judged checks, or none, are skipped). If they all pass and nothing was resolved, `checkpoint.sync` is recorded at once. If one fails, the merge is kept and the sync opens in the resolve phase with no conflicted file: `bf next` issues `resolve-sync` with `failing_checks` and `may_change`, and the brief carries the failing check's command and output tail. The directive holder may change, inside the checkpoint's working copy, any file that either side changed since the merge base (the stack's side or the main branch's side) and new test files beside them (a file with `test` in its name in the same folder, or any file in a folder named for tests); nothing else. The guard and the report-time check use that same set (the report compares the working copy with git's own automatic merge and refuses a changed file outside it). The resolver runs only the tests it changes, selected by name, fixes what fails, commits and reports `built`; the engine runs the sync's checks before the sync goes to review, and refuses the report while one fails, naming the sync check and its command. The reviewer of a sync lists which checks the sync ran, and on which content, with `bf evidence verify --checkpoint <K>`; a sync check missing or failing there is a finding. The reviewer's brief shows the whole fix (resolution and repairs) against the automatic merge result; rounds, parking, `--release` and `--abort` are the same. When the checks pass and the review is clean, `checkpoint.sync` is recorded; the sync's runs do not count as the checkpoint's receipts, and the checkpoint's own receipts from before the sync started are put out of count, so the checkpoint's own checks run again at verification on the content being closed. This was built into the sync's own small state machine rather than as an engine-made unit, because a unit would have to be a plan record (its files and checks fixed by the plan gate, so frozen-record drift and amendments would apply to something the human never planned); the owner-facing behaviour is the same.

**A merge conflict is resolved by the factory's own agents; the human's part is the one sentence that asked for the sync.** The command does not abort: it leaves the merge in progress in the checkpoint's working copy (in each repository that conflicted), appends `checkpoint.sync.open` (the repositories, the main commit, the files in conflict, where each branch stood before) and exits 0 with the conflicted files (`--json`: `sync_open: true`, `conflicted`). The run is then in a sync-resolving state for `K`: **no unit starts and `K` does not close until it is settled**. `bf status` (`sync_open`: checkpoint, phase, rounds, files; plain status prints a `note:`) and `bf next` show it, so a resumed or new session finds it alone.

- `bf next` gives one directive. **`resolve-sync`**: `role: "builder"`, the policy's builder `tier`, a one-use `token` (as for other worker directives), `checkpoint`, `working_copy` (the checkpoint's working copy folder), `brief`, `limits`, `files` (the conflicted files, paths inside that folder, prefixed by the repository name when several are touched), `commands`, `abort_command`. `bf brief <K> --role builder` writes the brief: the files, what the stack changed and what the main branch changed in each (from git), the rule that only those files may change, and how to finish (remove every marker, `git add` them, `git commit --no-edit`, then `bf report <K> --role builder --result built --token T`, or `--result blocked --note "why"`). The conductor may hand it to a builder agent or do it itself: both go through the same directive and token.
- The guard, while the sync is open: from the checkpoint's working copy the Write and Edit tools may change exactly the conflicted files, `bf report` is allowed, and `git add` and the concluding `git commit` are as they always were there; everything else in a checkpoint's working copy stays denied, and so do `git merge --abort`, `git reset --hard`, `git stash` and the like (the engine aborts, not the agent). The engine does not rely on the guard alone: at the report it checks (refusing, with the usual four parts, until it holds) that no unmerged path and no conflict marker remains, that the merge is concluded with a clean working copy and holds the main branch's commit, and that, compared with git's own automatic merge (`git merge-tree --write-tree`), only the conflicted files differ.
- Then `bf next` gives **`review-sync`**: `role: "reviewer"`, the policy's reviewer tier, a token, and a brief (`bf brief <K> --role reviewer`) that shows each conflicted file's resolution against both sides. The reviewer reports `--result findings --findings -` (a JSON list of `{title, where, action}`) or `--result built` (clean). Findings send it back to `resolve-sync` like a unit's fix round, within `[limits] max_rounds`; over the limit, or when the resolver reports `blocked`, the sync is **parked** and `bf next` gives a human directive `decide-sync` with `release_command` and `abort_command`. The human releases it with `bf checkpoint sync <K> --release --quote "..."` (words, like an approval; rounds start again). The release of a parked sync takes only words written after it parked, and a hand-resolved sync only words written after it opened, each no earlier than the floor, in the command and in the replay; the start takes the human's request as before.
- A clean review makes the engine record `checkpoint.sync` as for a clean merge (the checkpoint's own checks reopen, later units start from the new tip, the main-branch note goes quiet).
- `bf checkpoint sync <K> --abort` puts every repository's checkpoint branch back as it was before the sync started and appends `checkpoint.sync.abort`. It needs no human turn (it only returns to the proven state) and is for the conductor as well.
- The human's own way stays: resolve the merge by hand in the working copy, `git commit`, then `bf checkpoint sync <K> --resolved --quote "..."`; with a sync open it checks the same things as the report and records the sync with the human's words. (A conflict in a file the guard protects, for example a record under `factory/` in a project folder, cannot be written by an agent; abort or resolve by hand.)

A `checkpoint.sync` event (checkpoint, repository, the main branch's commit, the merge commit) is appended; units that start afterwards start from the new tip; the receipts of `K`'s own checkpoint checks that exist then stop counting (the content changed) and the checks are open again; the receipts of landed units still count for their units; the recorded main commit of that repository moves to the main branch's tip, so the quiet main-branch note goes away, and the final `--merge` onto the main branch has nothing foreign between.

**A hand merge without the command.** Merging the main branch into the checkpoint branch by hand in `.bf/work/<K>` is not refused by the engine (an agent's `git merge` there is refused by the guard, so it is the human's step). Nothing is logged; the checkpoint's own receipts are for the old content and stop counting; the unit receipts stay; the main-branch note stays until something records the position. `bf checkpoint sync <K> --resolved --quote ...` after the hand merge records it.

### The review of a checkpoint: repeat reviews, areas, probes and the stop rule

The first review of a checkpoint is cold: it gets the whole diff and the brief of every unit, and nothing else. A repeat review (`bf brief <K> --role reviewer` after the content changed) gets the same, and also the report of the review before it (its areas, its probes and its findings), what became of each finding, the probes kept from every review before it, and the difference since the content that review looked at. Its scope is still the whole checkpoint. It first confirms that each finding marked fixed is fixed, then reviews the changed code, then takes angles the reviews before did not take. It files only new problems: a finding the human accepted, or declined with a reason, is refused if it is filed again (same title and place). This replaces, for the review of a checkpoint, the rule that a later round does not review the whole scope again.

What became of a finding is one of three: **fixed** (with the unit or units whose files the fix changed), **accepted** by the human, or **declined** with a reason. Both of the human's endings need their own words: `bf checkpoint finding <K> --accept <ids|low> --quote "..."` and `--decline <ids> --reason "..." --quote "..."`. Ids are `r<round>.<number>`; `low` means every open low finding of the latest review. `--fix-findings <ids>` picks findings to be fixed: it opens the checkpoint fix for them. **A finding's fate is its own.** A fix records the round and the number of each finding it was opened for, and a finding counts as fixed only by a finished fix that names its round and number: a finding filed again word for word by a later round is open on its own. A fix recorded before the pairs were kept still matches by value, but only findings of rounds no later than the one it was opened from. A fix that ends without passing its review (`bf checkpoint fix <K> --abort`) leaves its findings open, and `bf next` then offers no new review: whatever the checkpoint's content now is (a sync of main may have changed it), while a high or medium finding is open and no fix, no review round and no parking is, it asks the human (`decide-checkpoint-fix`) to open the fix again with `--fix-findings <ids> --quote "..."`, or to accept or decline each finding in their own words. `--fix-findings` is refused while the checkpoint is parked, naming `--release`, and picking a critical, high or medium finding needs the human's words (`--quote`, taken from one human message once, like `--accept`); picking only low findings needs none. `bf checkpoint close` names an open high or medium finding that holds it (`r<round>.<number>`, its severity and title) and `bf next`. **Each of the five decisions (`--fix-findings` of a critical, high or medium finding, `--accept`, `--decline`, `bf checkpoint review <K> --release` and `bf checkpoint fix <K> --release`) takes only a human message written after the event that put it to the human**: for a finding, the later of the report of its round and the abort of the latest fix opened for it (the latest over the findings named); for the review `--release`, the report of the round that parked the checkpoint; for the fix `--release`, the park of that fix. **The human is not being asked about a checkpoint's findings while one of seven holds lasts**: a sync of main into any checkpoint is open (every phase, parked included); any checkpoint fix is at work (open and not parked, the gap phase included, whatever it was opened for and whichever checkpoint it is of); a check of the checkpoint is marked failed or unreachable at its content, so `bf next` gives `decide-check`; a worker's question on the checkpoint is unanswered; a wave check holds the checkpoint's close; the latest plan gate of the run is not approved, so `bf next` asks only about the gate; or the budget cap is reached. The last two hold for every checkpoint and come from the same function as `bf next`'s early return; the human is not asked about findings then, and each ends by the gate's decision or by the human raising `budget.cap`, the floor moving at its end. `bf next` offers no decision on a finding then (it offers `decide-checkpoint-review`, `decide-checkpoint-fix` and the low-finding directive only when nothing holds; the low decision is offered whenever a low finding is open and nothing holds, so a low finding is never settled on words written while it was not asked), and each of the five decisions is refused, naming the hold, the command or step that ends it and `bf next`. **`bf checks set` that switches the checkpoint review off for the run** is a sixth way to end the findings' hold: while a checkpoint has an open critical, high or medium finding it is refused during a hold, and it takes only human words written after the floor, in the command and in the replay, since the human is not asked then. **Every bound is also no earlier than the end of the latest hold of any kind**, so words written during a hold stay refused after it ends, and a new message then decides. The engine writes a `checkpoint.hold` event at each start and end of a marked check, an unanswered worker question or a wave hold that it observes (at `bf next`, at each of the five decisions and after each event that can start or end one: each abort, each opening of a sync or a fix and each gate event, so a hold an abort brings back is logged before the next decision), so the replay applies the same predicate through the same function; a K-1 log replays unchanged; a later log replays unchanged unless it holds a decision taken during a hold, which the replay then lists as ignored with its cause. The replay of a review release sets aside only the fix that release itself opened. An older message is refused, and the refusal says the words were written before the decision was put to the human and asks for a new one; words already used for another decision are refused as used. The replay applies the same bounds from the same state: one function gives this rule to the commands and to the replay, and the replay lists each ignored event with its cause: a hold (naming it), words written before the bound or already used, a decline with no reason, or a fix release of a fix that is not parked. An ignored event leaves its finding open. `bf brief <K> --role reviewer` is refused while `bf next` gives `decide-checkpoint-fix`, so no review starts while the human is asked.

**Every report says which areas were probed and how.** The reviewer reports through `--findings -` with a JSON object: `{"areas": [{"area": "...", "how": "read"}], "probes": [...], "findings": [...]}`. `how` is `read`, `built and run`, or `probed with a test of its own`. A report with no areas is refused, with findings or without. The list is kept with the review, given to the next review, and shown on the checkpoint page.

**Probes.** Every probe test a reviewer writes goes in `probes` with `name`, `meant` (what it was meant to show), `showed`, and `file` (its path inside the reviewer's copy), `command` and `expect` (the right answer). The engine stores the file under `factory/evidence/probes/<K>-review-<n>/`, apart from the checkpoint's code. A probe holding a home path, a link, an e-mail address or the name of the person at the machine is refused. A finding that a probe exposed names it in `probe`. The checkpoint fix for that finding must add the probe to the suite as a permanent test: the builder's `built` report is refused until the file is committed in the checkpoint's working copy, holds the stored probe, and its command gives the expected exit (`expect_exit`, 0 by default).

**When a checkpoint may close.** It cannot close while a critical, high or medium finding of any review since the human last released it is open, and it cannot close while a fix of it is open, whatever opened the fix (`bf checkpoint close` names the fix and `bf next`). A review that files none lets it go on to its close; its low findings are listed for the human (`decide-low-findings`), who accepts them together or picks some to be fixed, and they never hold the checkpoint back. The number of reviews a checkpoint may have is `[limits] checkpoint_reviews` in the policy (3 as shipped). When it is reached with a high or medium finding still open, the checkpoint parks: no fix opens, no new brief is written, and `bf next` asks the human (`decide-checkpoint-review`). Only the human releases it, in their own words, from a message written after the report that parked it: `bf checkpoint review <K> --release --quote "..."`. The reviews so far then stop counting, and the open findings go to a fix. No review starts while an open high or medium finding waits for the human's decision (`decide-checkpoint-fix`): the brief is refused.

**The checkpoint fix.** A fix for failed checks or findings runs in the checkpoint's own working copy and parks when its builder reports `blocked`, its attempts reach the limit or its review rounds do. A parked fix waits for the human: `bf checkpoint fix <K> --release --quote "..."` takes only a human message written after the fix parked, so words written before the plan or while the fix ran do not release it. `bf checkpoint fix <K> --abort` needs no words. The replay ignores a release that cites an older message, and a release of a fix that is not parked; the fix stays as it was.

**The checkpoint fix's path in R-70.** `bf checkpoint fix <K> --open` reopens a fix for a failed check of the checkpoint's current content when none is open. A fix of only a failed format or lint check ends with no review round once every change is accounted for, and files accepted as format only carry that mark. A fix's builder asks for files beyond its list with `bf report <K> --role builder --result blocked --token T --need-files -`; the scope reviewer's verdict (`bf checkpoint scope <K> --verdict <f|->`) grants them for that fix only (`needed`), sends the builder back (`retry`, with `must`) or leaves the file to the human (`extension`). The file list is read live, so a grant counts at once. An aborted fix saves its work, and the next fix of the checkpoint starts from it. The human may accept any finding of a parked review or fix in their own words.

### `bf human-turn`

For the harness's `UserPromptSubmit` hook. Reads the hook payload on stdin and, when it is a message the human typed, appends a `human.turn` event with the text. It prints nothing, except the note about the context share and the refusal of a required model (below), because a hook's output goes to the model. It always exits 0 on a recorded or rejected message, and 1 on an error; it never exits 2, because that would erase the human's prompt.

A payload is **not** a human turn when: it does not say `hook_event_name: UserPromptSubmit`; it has no `session_id`; it carries `agent_id`, `agent_type`, `parent_tool_use_id`, `subagent` or `agent_name`; its `source` is set and is not the user; the prompt is empty; the prompt is the host's own message and not the human's (below); its `cwd` is outside the project or inside a unit's working copy; or the policy lists the human's session ids (`[human] sessions`) and this one is not among them. Rejected payloads are logged as `human.turn.rejected` with the reason (it names the form that matched) and never satisfy anything.

**What is the host's own message.** After removing any leading `<system-reminder>...</system-reminder>` blocks and surrounding whitespace, a prompt is the host's when the WHOLE of it is one of: a `<task-notification>` element (a background task finished); an `<agent-message from="...">` element (a subagent's hand-back or another agent's message); a `<cross-session-message ...>` element (another session's message); a `<side-sessions-event>` element; a `<ci-monitor-event>` element; the sentence `The app was quit while you were working. Please continue from where you left off.`; or text that starts with `Background (from the session that started this one):` or `Task (from the session that started this one):` and a newline (the brief a session is started with). An element must start the prompt and its first closing tag must end it (`</name>`, with `<~/name>` or `<\~/name>` also read as closing the two message forms, and a `~` or `\~` after the `<` of the opening tag ignored), so a message of the human that contains or quotes such a block inside other words is still theirs. A prompt made only of reminders is the host's too. Prompts that start with a `<local-command-stdout>`, `<local-command-caveat>`, `<user-prompt-submit-hook>`, `<teammate-message>` or `<channel>` wrapper are not the human's either. The human's pasted text (`<pasted_content`) and a message sent while a turn is running arrive on their own and count. **The transcript row, when it can be found** (the payload's prompt id, and exactly this text), gives a second signal by its own marks: host when `promptSource` is `system`, `turnOrigin` is `task_notification` or `peer`, or `origin.kind` is `task-notification`, `coordinator`, `peer` or `auto-continuation`; human when `origin.kind` or `turnOrigin` is `human` or `promptSource` is `typed`. A host mark rejects whatever the words, a human mark accepts whatever the words; a row with neither mark (the desktop app marks its own notes and the human's alike as `sdk`) decides nothing and the words decide. The CLI writes the row after the hook returns, so often there is none yet: its absence decides nothing.

**The transcript is information, not a gate.** The turn is recorded from the payload as given. The engine also looks at the transcript file the payload names and stores what it saw with the turn (`transcript`): `match` when the last human message in it is this prompt; `differs` when it is another one; `unparsed` when no human message could be read; `absent` when the payload names no transcript, the file does not exist, or it is not under `[human] transcript_root` (default `~/.claude/projects`). Claude Code writes the transcript after the hook runs, so for the first prompt of a session the file is absent and for a later one it ends with the previous prompt: `differs` and `absent` are the normal values. Lines of type `api-request-blob`, meta lines and tool results are not counted as the human's message. `bf gate status` and the gate page show the value beside each decision. A policy that sets `[human] transcript_match = "strict"` refuses a turn unless the transcript already ends with the prompt (for a harness that writes it first).

The engine cannot tell a person from a program that writes to the hook's input. The hook is the source of human turns, the checks above remove the obvious fakes, and the quote on every decision (below) makes it visible which words were taken. See "What the engine does not stop".

### `bf gate open <kind> [--ref ID]` / `approve` / `reject` / `skip ui` / `status`

Kinds: `idea`, `requirements`, `ui`, `architecture`, `plan`, `checkpoint-step` (needs `--ref K-<n>`). A gate has rounds; its ID is `<kind>-r<round>` (or `<kind>-<ref>-r<round>`). Opening records a snapshot of the records the page shows, so the next round can mark what is new, changed or removed.

**Design gates open in order and never empty** (`[gates] in_order`, on by default; the same in a granted test run, with simulated approvals). The order is idea, requirements, ui, architecture, plan: `open` refuses, with the usual four parts, while an earlier gate is not approved (a rejected gate's next round is not held by this), and when the stage has nothing to approve: idea needs an idea record or `factory/idea.md`; requirements at least one requirement; ui at least one screen or journey; architecture at least one component and one decision; plan a plan that passes `bf plan check` with at least one unit and one checkpoint. A product with no interface has no screen to invent: `bf gate skip ui --quote "<the human's words>"` (a decision like an approval, once) records the skip in the log; a skipped ui gate counts as passed for the order, and `bf status` (`skipped_gates`), the index page and the architecture page say so. An architecture gate with no threat record opens, and its page carries a visible caution that no threat was recorded.

`approve <gate> --quote "<words>"` and `reject <gate> --quote "<words>"` need a human turn recorded **after** the gate opened and not yet used for anything else. One typed message decides one thing. **The quote** is the words of the human's message that the conductor read as the decision. The conductor's reading of the human's words is intended; the engine does not second-guess it. It checks only what it can:

- the quote is in the human's message (and is not empty);
- an approval (`approve`, `test-mode grant`, `amend approve`, `policy accept`, `head accept`, `unit release`) is not a question: the quote does not end with `?`, and the message is not only questions;
- a test-mode grant also speaks of a test run.

The quote is stored with the decision, and so is the human's **whole** message. `bf gate status`, `bf gate approve --json` and the gate page ("Decided on the words", "The human's whole message") show both. When the message also holds a word that can point the other way (the policy's `[human] refusal_words` for an approval, `approval_words` for a rejection: *not*, *wait*, *change*, *later*, *cannot* and so on, in English, German, French and Spanish), the gate status and the page show a **caution** ("the message also contains a word that can mean no: \"wait\""). The lists never refuse anything. `approve --simulated` is described next. A bare kind (`plan`) means its latest round.

`bf gate open` prints the gate ID. `bf gate reject` closes the round; the next `bf gate open <kind>` starts round n+1.

```bash
bf gate open architecture
# the human says "I approve the architecture" in chat; the hook records it
bf gate approve architecture --quote "I approve the architecture"
```

Refuses when: opening the `ui` gate while the design-stage UI/UX verification (`named = "design-uiux-verification"`) has no receipt for the screens as they are now; opening the `architecture` gate while no threat is recorded and the threat model check is on, or while no markets statement exists and a legal check is on (`bf record put markets`; an empty list is a statement of no market); no quote is given, or it is not in the message; an approval is a question; the kind is unknown; a gate of that kind is still open; unanswered questions are tagged for this stage (see `bf questions`); for `plan`, the plan has problems; no human turn follows the open; the gate is already decided.

### `bf test-mode grant`

A grant for one run, made from the human's latest message (it must be unused). If a run is active it applies to that run; otherwise to the next `bf run start`. A grant that is waiting for its run also lets the five design gates (`idea`, `requirements`, `ui`, `architecture`, `plan`) be approved with `--simulated`, so a test run can go through them in order before `bf run start`; the checkpoint-step gate needs the run. Inside a granted run, `bf gate approve <gate> --simulated` satisfies a gate and is recorded as simulated. Outside one it satisfies nothing: the command refuses, and an approval event written into the log by other means is ignored when the state is replayed.

Needs `--quote` like an approval. Refuses when: the human's latest message is missing, already used, only a question, or does not contain the quote.

### `bf view <kind> [id] [--json]` / `bf render <kind> [id] --template <file> --out <file>`

`view` prints the page data in the view contract (version 1, `contract: 1`). Kinds: `index`, `gate` (id is a gate ID or kind; a kind never opened gives a draft page), `questions` (id is a stage), `ledger`, `plan`, `run`, `checkpoint` (id is a checkpoint), `coverage`. The output is always JSON.

The `index` page is a list of pages: sections of rows, each with `href` and `meta`. The links follow one naming convention, so a conductor that renders each page under that name gets working links: `gate-<gate id>.html`, `questions-<stage>.html` (one page per stage; the old name `questions` is still read), `plan.html`, `run.html`, `ledger.html`, `coverage.html`, `checkpoint-<K>.html`.

`render` also sets the page title: if the template's title is `<title>Black Factory</title>` it becomes `<page title> · Black Factory`, and a `/*BF_TITLE*/` marker, if the template has one, becomes the page title.

`--out` is resolved when the file is written, links included: a path that leads into the state folder, `factory/`, `.git/`, the transcripts or the private part of `.bf/` (anything but `pages/`, `drafts/` and `work/`) is refused. `render` puts the JSON into an HTML template at the marker `/*BF_DATA*/` and writes one file. If a literal placeholder (`null`, `undefined`, `{}`, `[]`) follows the marker it is replaced too, so `const DATA = /*BF_DATA*/ null;` works. The JSON is made safe for a script element (`</` and line separators are escaped).

```bash
bf render gate architecture --template views/templates/page.html --out out/architecture.html
```

Refuses when: the template cannot be read or has no marker; the page kind is unknown; no gate matches.

### `bf ask --file q.json [--stage S]` / `bf ask --title T [--unit U]` / `bf answer <Q> --file a.json` / `bf questions [--open]`

A stage's questions come before its gate. `ask` takes a JSON list of questions in the view contract's shape without IDs: `[{"title", "kind": "single|multi|text", "context", "stage", "options": [{"key", "text", "proposed", "why"}]}]` (a table with a `questions` list, or one question, also works). The engine assigns `Q-` IDs and prints them; a bad entry writes nothing. `--stage` fills the stage of entries that have none. `answer` needs a human turn recorded after the question was asked (the turn is stored as `answered_turn`), and takes one file per question, for example `{"choice": "A", "note": "..."}`, and stores it as the answer (or the file's `answer` value if it has one). `questions` lists them.

A question is **tagged**: a stage question (`--stage`, or `stage` in the file) holds that stage's gate; a **unit question** holds only its unit. A builder, reviewer or verifier asks from its working copy with `bf ask --title "..." [--context "..."] [--options "A=first;B=second"]` (no file needed; `--file -` or a file also work) and is tagged with its own unit or checkpoint; the conductor can tag one with `--unit U-<n>`. `bf next` shows each open unit question as a human directive (`answer-question`) and offers no directive for that unit until the human answers; other units go on. The answer reaches the worker in its next brief (`## Questions you asked the human`). A question with neither a stage nor a unit is refused, with the recipe, because nothing would wait for it.

**Every choice question takes an Other answer.** `other` (lowercase) is a reserved choice key: `bf ask` refuses a question whose own option uses it, and a question may carry `"other": false` to switch Other off (stored on the record; text questions have none). `bf answer <Q> --file a.json` accepts `{"choice": "other", "other": "<the human's own answer>", "note": "..."}` for a `single` question and `{"choices": ["A", "other"], "other": "<text>"}` for a `multi` one; choosing `other` with empty or missing text is refused, choosing it on a question with Other switched off is refused, and `other` text without the key chosen is kept as given and does not count as the choice. The text is stored in the answer's `other` field and is what every listing shows: `bf questions`, the briefs that quote answers and the questions view (whose `answer` object carries `other`, and whose question carries `other: true|false` for choice questions) show the human's text, never the bare word "other". Earlier records, with no `other`, read as they did.

### `bf amend open <ID>...` / `revise <ID>...` / `narrow --file f` / `approve [A-n]` / `withdraw <A-n> --reason "..."`

Only one amendment is open at a time. `open` is refused while one is open (not approved, not withdrawn); the refusal names it and says to revise or withdraw it. `revise <ID>...` changes the records the open amendment covers; it keeps its ID, its narrowing is void, and `narrow` (which takes the open amendment when the file names none) and a human message after the revision are needed before it can be approved. `withdraw` drops an amendment that is not approved and needs a reason; the log keeps that it existed and that it was withdrawn, and it can no longer be narrowed or approved. A withdrawal puts back, for every record the amendment named or touched, the content last approved (found in the log by its hash; it is refused, naming each record, when one cannot be found) and takes out a record the amendment added. `bf log` leaves the record contents of amendment events out and prints `[contents left out]`; `bf log --whole <number>` prints one event whole. The status and the pages list each amendment as open, approved or withdrawn. On replay an approval counts only with a human message after the amendment's latest narrowing or revision.

`open` computes the impact set from the ledger. `narrow` takes `{"keep": [...], "waive": [...], "reasons": {"<ID>": "why"}}`: it may only remove IDs from the set, every removed ID needs a reason, and every waived ID needs a reason. `approve` needs a human turn after the narrowing. An amendment lets the records it names (its own new or changed records, not the kept impact set) be put while it waits for the human, and the one approval covers the content put; after the approval a change needs an amendment again. A kept record that must change is moved to the changed set, in this order, the order in which the engine accepts the steps:

1. `bf amend revise <the IDs the amendment names now, and every record that changed>`. Revise replaces the whole set, so name every ID again, the kept record that must change among them. The engine's refusal says the same.
2. Put the record (`bf record put <kind> --file <f> --replace`).
3. `bf amend narrow --file <f>`.
4. The human's yes, in a message written after the narrowing.
5. `bf amend approve --quote "<their words>"`.

**Narrowing presents everything that differs.** `narrow` works out every record of the set (its own records, the records its operations touch and the kept impact set) whose content differs from the content last approved (the plan gate's snapshot, or the latest approved amendment's content), a kept record included, and a record that is new or gone. It stores that list with the narrowing and records the fingerprint of exactly that list and the set; each entry holds the record as it is now and the content last approved (kept in the plan gate's snapshot and in the approval's content), and the fingerprint covers both. The amendment page shows the stored list and **every field that differs**, old value then new value, for every kind of record (a unit's `own_checks`, a checkpoint's `stop`, a check's `named`, every field of a handoff, and the rest); a field on one side only shows as added or removed, a new record shows its fields as added and a removed one as removed. The page reads the stored list and does not work it out again, so the human reads what the fingerprint covers. The fingerprint covers the kept records too, so `bf amend approve` is refused when any record of the set, a kept one included, changed after the narrowing the human read, by any route (an edit of the file outside `bf record put` too). Its `waive` list stands in for a receipt at `checkpoint close`.

**The drafts of an amendment.** A draft of an amendment that is not approved has no force: nothing in it is the record in force until the human approves the amendment, and a withdrawn amendment leaves no force behind. The hash of the threats (`threats_hash`) covers the id and the content hash of every threat record, in the order of their IDs, so a change to any threat, or a threat added or removed, makes the security expert's report stale and it must be given again. The human's words count for lifting the designer rule only when they were written after the amendment was opened (for a stage, after the gate before it was approved), they are used once, and a lift made earlier does nothing.

**A draft has no force.** A unit, a check, a checkpoint or a handoff of the approved plan that an amendment waiting for the human changes is a **draft**, not the record in force: `bf evidence run` is refused for it (`a draft of the plan is not the record in force`), its file list grants nothing, a checkpoint record that is a draft does not close, and no unit lands while a check of the approved plan that belonged to it is a draft, whether the draft changed, deleted or moved the check to another unit or to checkpoint scope. All of it waits for the human's approval of the amendment. The record in force is the content the human approved: what the plan gate approved, or what the latest approved amendment covering the ID approved when that came later. The approval stores the hash of every record of its set (`content` in the `amend.approve` event), so an approved amendment covers that content and no other: a record changed again after the approval, with no amendment open, is a draft too, `bf record put` refuses it, and the plan is frozen again (`bf doctor` names the record) until an amendment the human approves covers it. The same holds for what a withdrawn amendment left changed. Putting back exactly the approved content needs no amendment, and a record the amendment named before it existed is put while the amendment waits (a put after the approval is refused, R-43), so the approval covers the content put. An approval recorded before the content was kept covers its IDs as it did.

**The stage coverage of a design amendment.** A design amendment covers each design stage in order (requirements, ui, architecture, plan): with its new or changed records, or with one sentence that says the stage is **not affected**. The sentence is a decision record made by the agent (`maker = "agent"`) that names its stage (`stage`) and is named in the amendment's set when it is opened or revised. `bf amend approve` is refused, naming each stage, while a stage has neither, and while a requirement of the amendment has no link to another design part; it is also refused when the records no longer match what the human read at the narrowing. The records an amendment's checkpoint operations change or create belong to the plan stage. The amendment page lists each stage with its records or its sentence. See [records.md](records.md) for the decision's fields.

**A plan repair.** `bf amend open --repair <ID>...` marks the amendment as a plan repair: a change to a check's command, a unit's file list or order, or moving a unit between checkpoints. It is refused when the set holds a design part (a requirement, screen, journey, component, threat, target or decision), naming each. An amendment that holds checkpoint operations and no design part is a plan repair without the mark. A plan repair needs no designer and no amendment review (see below), and takes effect when the human approves it, or, when the repair judge passes it inside the engine's limits (see below), with no human message. A repair the judge does not pass goes to the human.

**The judged plan repair (D-90).** A narrowed plan repair that is not `human_only` may be judged by a subagent of type `repair-judge` instead of waiting for the human. `bf next` gives the conductor `judge-repair` (work `amender`: strong tier, high effort, the model the policy names). `bf roles token <A-n> judge` issues one one-use token for each narrowing, and none after an earlier judge turn of the amendment ended with no verdict. It is refused for an amendment with a design part (each part named), for one that is `human_only`, for one whose narrowing changes a record of an `ask` the human has not seen, and when `[review] repair_judge` is off. `bf amend judge <A-n> --file <f|-> --token T --model M` takes `go` or `ask` with reasons in plain words; it puts no record and does not narrow, and it is refused without a fresh one-use pass that the guard wrote for a subagent of type `repair-judge`, and when the installed role file differs from the harness copy. The subagent is refused every write, `bf record put`, `bf amend open|revise|narrow|checkpoint|approve|withdraw` and `bf roles`.

- **Limits of a `go`.** The engine approves with no human message only when every changed record changes only a unit's `depends_on` (entries added only), `estimate` or `files` (an entry moved between two units or a new test file, never one that overlaps a protected path); nothing is added, deleted or waived; no landed unit or closed checkpoint changes; the approval adds no plan problem and leaves no unit depending on a unit of a later checkpoint (unless the plan had that pair); no checkpoint's scope changes by more than `judge_scope_percent` (30), counted over this repair and every judged repair of that checkpoint the human has not seen; and no checkpoint is left with a run of more than `judge_chain_waves` (3) waves that hold one unit of it each, unless the run was that long before and did not grow. Otherwise the go is refused, naming each failed limit. The scope measure is an upper estimate: a file moved between two units counts both units whole, so a small checkpoint sends most file moves to the human.
- **Events.** `amend.judge.token`, `amend.judge` (verdict, reasons, model, session, agent and the measures before and after), `amend.judge.failed` (the reason a turn ended with no verdict) and `amend.judge.seen`. `bf log` prints them with record ids only. On replay an approval by the judge counts only after a `go` for the amendment's latest narrowing with a token issued to the role `judge`.
- **The guard pass.** The guard writes a pass only when the hook payload names the agent type `repair-judge`. A missing type writes none, `bf amend judge` is refused, and the repair is the human's with one judge turn spent.
- **After an `ask` or a failed judge.** The amendment waits for the human and is never judged again, also after a revision. `human_only` binds records: every record that the narrowing of an `ask` or of a failed judge lists as changed stays the human's, also when that amendment is withdrawn, until the human says in their own words that they saw it (`bf amend seen`). A later repair that changes such a record gets no judge token. While an amendment is open, a not yet started unit it adds or touches is not ready.
- **The seen list.** Every repair the judge approved, every `ask` and every failed judge (withdrawn ones included) is listed with its reasons in `bf next` and on the run page until the human has seen it.
- **The switch.** With `repair_judge = false` every plan repair goes to the human. A repair opened with `--from-design <K>` from a fix design's item marked for a change of the plan is never judged.
- **Stated limit.** The agent type is the one the harness puts in the hook payload. The engine trusts it and cannot check it.
- **The ui stage.** No screen or journey changes: the judged repairs, a fix's grants and the accepted findings are rows of the existing run, checkpoint and amendment pages.

### `bf amend checkpoint before|after|split <K-n> <U-n>... [--title T]`

Inside an open amendment the engine can insert a checkpoint between two others, or split one in two, by renaming the later checkpoints one number forward. `before K-3 U-7 U-8` puts the units on a new checkpoint under the number `K-3`, and `K-3` and every later checkpoint become one number higher; `after K-3 ...` puts it under `K-4` the same way. `split K-3 U-4` keeps `U-4` on `K-3` and puts the rest of `K-3`'s units on a new checkpoint right after it. The numbers always read in the order of the plan.

```bash
bf amend open --repair U-7 U-8
bf amend checkpoint after K-3 U-7 U-8 --title "Export"
# renamed: K-4 -> K-5, K-5 -> K-6   created: K-4
# plan_problems: []
bf amend narrow --file narrowing.json
# after the human's words:
bf amend approve --quote "<their words>"
```

- A renamed checkpoint keeps its title, its units, its list of proven parts, its checks and its stop for the human, and every unit and check that named it follows the new number. The new checkpoint takes the stop of the checkpoint its units came from (`stop`, `stop_why`, `human_step`, `unit_checks`).
- A rename is recorded with the old number, so the amendment page shows the checkpoint as **moved** and not as changed, and the human's read marks follow it. This is the one exception to the rule that an ID never changes, and no other kind of record can be renamed.
- For the inserted checkpoint the engine also works out **a check of the whole checkpoint**: each command check of the units that go onto it (scope `unit`), copied once for each distinct command, with scope `checkpoint`, listed by the new checkpoint and proving what its units deliver; and **the order of units that share files**: two such units of the new checkpoint with no order between them are put one after the other, in the order they were named.
- Only a checkpoint that has not started can be renamed or lose a unit: one that is closed, or holds a unit that has started, is refused by name. A checkpoint left with no unit or with nothing to prove is refused too, and so is a unit with no command check that proves what it delivers.
- The change is part of the open amendment (`amend.checkpoint` event), counts as a plan repair when no design part changes, and **takes effect only when the amendment is approved**, by the human or, for a plan repair the judge passes inside its limits, by the engine; until then nothing is written. The plan check runs on the result at once (`plan_problems`) and again before the amendment can be approved, which is refused when the result breaks the plan.

**An approved amendment re-opens what it touches.** Every unit in the kept impact set whose work is not all waived goes back to work (`running`; what it landed stays in the log; its rounds and attempts start again; its brief and directive name the amendment), every checkpoint that proves a changed ID or comes after a re-opened unit opens again, and the receipts of the changed checks that exist at the approval stop counting (newer ones count). The ledger therefore reads open until the new evidence exists. Units and checkpoints outside the set keep their state and approvals, and `bf next` offers exactly the re-opened work.

### `bf review token|brief|split|finding|release`

The design review (R-97, R-98). Before a design gate opens, and before an amendment that is not a plan repair is approved, a cold design reviewer judges the records. Each kind of review has its own check record, a named check of the `review` family: `idea-review`, `requirements-review`, `architecture-review`, `plan-review` and `amendment-review` (the ui and legal stages have no check of their own; a stage of an amendment is judged under `amendment-review`). `bf checks list` shows them. A check the catalogue gained after the check settings were decided is off, with the reason `added after the check settings were decided; off until the human switches it on`, so a decision taken before these checks existed never silently turns one on.

- **What a review is bound to.** A review's receipt carries `review_kind`, `review_amendment`, `review_round` and `records_hash`: a hash of the records the kind judges (the idea also holds `factory/idea.md`; for an amendment, the records its set names and its stage decisions). A change to any record of the kind needs the review again, and a change to a record of another kind does not.
- **`bf review token <kind> [--subject A-n]`** issues the design reviewer's one-use token, and **`bf review brief <kind> [--subject A-n]`** writes its brief (the records it judges, the approved records of earlier stages they link to, the stage's questions with the answers, and the rules of its kind from the role file). The reviewer files findings (`bf record put finding`, with `gate` or `amendment`, and `asks` when it asks for a stage review) and settles the check with `bf evidence attach <check> <file> --outcome met|failed --says "..." --token T`; `met` is refused while a critical, high or medium finding of that review is open. The UI/UX verifier judges the `ui` stage of an amendment with its own token.
- **The holds.** `bf gate open <idea|requirements|architecture|plan>` is refused, naming each line, while the gate's review check is on and there is no review of the records as they are now, or the review is parked, or a critical, high or medium finding is open (the same test is `bf next`'s). `bf amend approve` is refused the same way while the review of the amendment is missing for its records as they are now, parked or holding an open finding of that weight; a plan repair is never held, and a review whose check is off holds nothing.
- **Rounds and the park.** A round ends with a counting review of the kind (for an amendment, of kind `amendment`). After `max_rounds` rounds with a finding still open, the review is **parked**: the engine records `design-review.park`, and a further outcome is refused. Only the human fresh-starts it: `bf review release <gate|A-n> --quote "<their words>"` takes only words written after the park, and the rounds start again. `bf review finding <gate|A-n> --accept <F-ids> --quote "<their words>"` accepts findings of that subject in the human's own words, never the conductor's; both are refused from a working copy. A finding stays on its review's token: another review cannot put or change it.
- **The shape of an amendment's review.** The general designer reports either a design of the whole amendment, which gets one solo review of kind `amendment` (which may ask, by a finding with `asks`, for a review of a stage, at most once per stage, and approval waits for it), or **a split**: `bf review split <A-n> --stage <stage>=<ID,ID> --token T` names the stages that get their own designer and the IDs each draws. The engine then issues a stage designer's token (`bf review token --subject A-n --stage <stage> --role <role>`) only for a named stage, at most one per stage and amendment, and a stage designer's records are accepted only for the IDs its stage was given. After a split, approval needs a review of each stage and then a review of kind `amendment` newer than all of them, which judges only that the stages agree.
- **Limit.** The conductor holds every token it passes on, since `bf next`, `bf review token` and `bf roles token` print them. A token tells roles apart and does not keep the conductor out, so it could settle a review in the reviewer's name; the conductor's instructions forbid it, and the engine cannot stop it. The human's words are the one thing the engine does bound: only they accept a finding or release a park, each from a message written after the event that asked.

### `bf checks list` / `state` / `propose <check>=off:<reason>... [--scope default|run|both]` / `set --quote "..."`

The named checks (security, legal, uiux families) are on or off for the project default, for one run, or both. `propose` records a proposal and changes nothing; it prints every check it would change, and each check switched off carries its reason. `set` records the latest proposal and is refused without a quote from a human message that came after the proposal (the quote is not a question, and must be in the message). Changes that differ from the proposal are refused. `state` and the pages show each check that is off with its reason. The project default is also mirrored to `factory/checks.json` (see the table above).

### The wave checks and the checks every unit must pass

Two questions are put to the human for every run, and no unit of a run starts until a human's words have answered both. `bf next` asks each question the run has not answered (`answer-wave-checks`, `answer-unit-checks`), before the plan gate and after it, and offers no `start-unit` meanwhile; `bf unit start` refuses a unit of the run and names the question. Before the plan gate, `bf plan check` also lists the unanswered one as a plan problem. A question the run has not answered may be answered once after the plan gate; an answer the run already has is frozen with the plan, and `bf amend open` is the way to change it. A run that began before the questions existed is asked the same way before its next unit starts. After the plan gate an answer must keep the plan's wave checks (the same commands) and leaves the approved records alone; `propose` and `set` refuse any other answer, before anything is recorded, and name `bf amend open`.

- **`bf checks wave question|propose|set|state`.** The wave checks are command checks that the engine runs on a copy of the checkpoint's content after each wave of units has landed. `question` prints the question to ask. `propose use-default|override "<command>"...|none [--scope run|default|both]` records a proposal and changes nothing. `set --quote "<the human's words>"` records the latest proposal and is refused without words of the human from a message that came after the proposal. `state` shows the project default and the run's choice. The conductor runs `question`, `propose` and `state`; only the human's words make `set` count; the project default is also mirrored to `factory/wave.json`.
- **`bf checkpoint wave-check <K> --wave <n>`.** The step the engine offers (in `bf next`) when a wave has landed and its check has not run on that content. The conductor starts it. It needs no worker's token and holds no lock while the checks run. A failure opens a fix held to the units that landed since the last pass, and no unit lands on the checkpoint until the check of the wave before has passed.
- **`bf checks unit question|propose|set|state`.** The checks every unit must pass, in the run: `propose project` uses the project's list, `propose override <name>=<command>...` gives the run its own list, `propose none` gives no checks. `set --quote "..."` records the proposal on the human's words, as for the wave checks. `state` shows the project's list and the run's choice. Only the run's choice is made here.
- **The project list** is `[unit_checks]` with `list = [{ name = "...", command = "..." }]` in `factory/policy.toml`, empty as shipped; only the human edits it.
- **Overrides.** A checkpoint (`unit_checks` with `unit_checks_reason`) or a single unit (`own_checks` with `own_checks_reason`) may override the list in its plan record, with a reason. The most specific list wins: the unit's, the checkpoint's, the run's, the project's. The plan page shows every override.
- **For one unit.** Each check of the list a unit is held to is run for that unit with `bf evidence run attached:<name> --unit U -- <command>` (the unit's brief gives the exact line); the unit lands only with a passing receipt for each, on its content.

A project that runs the default suite and the lint step on every unit lists those two commands in `[unit_checks]`. These are also the commands a sync runs (see `bf checkpoint sync`).

### `bf roles list` / `show <role>` / `token <unit|design> <role>` / `lift <stage|A-n> --quote "..."`

Eight roles are known by name besides builder, reviewer and verifier: `uiux-verifier`, `security-expert`, `security-auditor`, `lawyer`, `legal-auditor`, `design-reviewer`, `uiux-designer` and `designer`. `list` and `show` print each one's stage (`design` or `built`), what it may read, write and run, and its tier. `token` issues the one-use token of a role for a subject, and `bf brief <subject> --role <role>` writes its brief. A role works only at its stage. The security expert drafts threats (`bf record put threat`) and the security auditor files findings on the built result; the lawyer and the legal auditor write legal records.

**The auditors on a checkpoint, and the security expert as the proof of the threat model.** A built-stage role (`security-auditor`, `legal-auditor`, `uiux-verifier`) is briefed for a checkpoint (`bf brief <K> --role <role>`) and reports from the checkpoint's working copy with its own token (`bf report <K> --role <role> ...`); the guard lets a checkpoint's copy run `bf record put` and `bf report --role` for it, and the engine asks for the role's token. An auditor files a finding for its unit in any state once the unit has started, not only while it is in review, and for a checkpoint's auditor, for a started unit that the checkpoint comes after; it files only a new, open finding (a working copy never replaces a finding that is filed). The threat model is proven when threats exist **and the security expert reported at the design stage after the last change to any threat record** (`bf report design --result built --role security-expert --token T`): the architecture gate and the run's close refuse a threat model that is not proven, naming the expert's report.

**The designer (R-67).** A record of a design stage, or of an amendment that is not a plan repair, is accepted only with the token of the designer the engine issued for it: `bf roles token design designer` for a stage and `bf roles token <A-n> designer` for an amendment (a stage agent of a split holds a stage token instead), and the record is put with `--token T --model <the model the designer runs on>`. The engine keeps the model with every record it made (`design.made` event), and the pages show that the designer agent made it and on which model. A plan repair needs no designer. The human can lift the rule for one stage or one amendment in their own words: `bf roles lift <stage|A-n> --quote "<their words>"` records the quote, once per message, and the records of that stage or amendment are then accepted without a token and shown as made without a designer, with the words. The conductor does not draft design records itself and starts the designer on the model the policy names, without stopping and without asking. **Stated limits:** the model is the agent's own report, and the engine cannot check it; and the engine cannot see which model runs the conductor, so that the conductor starts a designer rests on its instructions.

**The human's words in a design review and for the lift count only when valid.** A `review.finding.accept`, a `design-review.release` and a `designer.lift` count only when the log replay accepts them: each cites a human message and quote that exist, unused, written after the work it answers (a release after the park, a lift after the amendment was opened or after the gate before the stage was approved, an accept after the latest review of the finding's kind). The parked state, the rounds, the findings' outcome, the release words on the page and the lift all read the replay's verdict, so an event appended to the log by hand that cites no valid message does nothing. The security expert's report on the threat model is bound to a hash of the threats as they stood: a change to any threat record after the report needs the report again.

**The design subject.** A design-stage role has no unit, so its subject is the word `design`: `bf roles token design <role>`, `bf brief design --role <role>`, `bf report design --result built|blocked --role <role> --token T`. The brief lists the design records, the report works outside a run and moves no unit, and a design-stage token ends when a run starts or stops. The UI/UX verifier works at both stages.

### `bf progress [--json]`

Prints the progress line of the run, one line: one segment per state, with a sign (`▶` building, `◐` in review, `↻` fixing, `●` reviewed, `✔` landed, `⚠` blocked or parked, `◎` checkpoint being verified, `■` checkpoint closed), the unit IDs and, for a unit in review or fixing, the round: `◐ U-3, U-4 in review, round 2`. When units in one state are in different rounds, each ID carries its own: `◐ U-3 (round 2), U-4 (round 1) in review`. The conductor shows this line and does not compose it. `--json` has it as `line`.

### `bf cost status` and the policy

`bf cost status` prints spent, cap, tiers and per-unit cost. `--cost` on `bf report` adds spend. When `[budget] cap` in `factory/policy.toml` is above 0 and spend reaches it, `bf next` and `bf unit start` refuse.

#### The model policy

The accepted policy names, for each kind of work, a tier (`cheap`, `standard` or `strong`), an effort (`low`, `medium` or `high`) and optionally a model for a harness outright. The kinds are: `conductor` (conducting the build loop), `designer` (a design stage), `amender` (an amendment), `advisor` (advising the conductor on a question that needs judgment), `builder`, `reviewer` (a unit), `checkpoint_reviewer` and `verifier`. The shipped defaults put the build loop and the builder and verifier on the standard tier and the design stages, amendments, advising and both reviews on the strong tier, in the `[tiers]` and `[efforts]` tables, with a model named in a table such as `[models.builder]` holding `claude = "<name>"`. Every directive `bf next` gives carries the `tier` and the `effort` of its kind of work (and a `model` when one is named); a unit's own `tier` still wins on its builder's directive. Advising has no directive and no token, because the advisor writes nothing to the engine: `bf policy` with no subcommand prints every kind's entry with the rest of the policy in force, and the conductor reads the tier, the effort and any model named there before it starts an advisor. The pages show the policy in force for a run. Only the human changes the policy, and a change takes effect when the human accepts it.

#### The context share

`[context]` holds `max_share` (percent of the context window a conductor's session may fill, 40 as shipped) and `max_age_seconds` (900: a saved share older than this is not used). The status line command (`bf progress` as the harness's status line) saves, per session in `.bf/session-state.json`, the share in `context_window.used_percentage`, the model in `model.id` and `model.display_name`, the effort in `effort.level` (a plain string `effort` is read too) and the time, each time the harness gives its input. On each message of the human, the `bf human-turn` hook adds a note to the conductor's context when the saved share of that session is above the setting: the share and the setting, and the instruction to finish the step in hand and then ask the human whether to start a new session, compact, or continue. The conductor does not compact by itself (on the answer compact, the human runs it) and on new session it starts it as the model policy says. **Stated limits:** when the harness gives no share, or the saved one is older than `max_age_seconds`, or the session has no status line command, no note is made and nothing is claimed; a share is the one at the last refresh; and that the conductor asks rests on its instructions, which the engine cannot enforce.

#### The required model

A message may start with a line `Required model: <model> [<effort>]`, for example `Required model: Opus 5.5 High`. On such a message the hook compares the line with the model and the effort the session runs on, as the status line saved them: the name must equal the model's display name or id as a whole (ignoring case and punctuation, an id may carry a leading `claude` and a trailing date), so `Opus 5` is not `Opus 5.5`. When they match, the message goes through unchanged. When the model or the effort differs, the hook refuses the message with no question asked: it prints `{"decision": "block", "reason": "..."}` and exits 0, the reason says which model and effort to switch to, and it repeats the whole text of the message so the human can send it again after switching. A message with no such line is not checked. When the hook cannot learn the session's model or effort, it refuses too and says what it could not read, so that a required model is never passed unchecked. **What the harness gives, and what it cannot do** (checked against the harness documentation for the status line and hooks): a hook's payload carries `session_id`, `transcript_path`, `cwd`, `permission_mode`, `hook_event_name` and `prompt` and no model or effort, so the hook learns them only from what the status line saved; the transcript names the model of past replies but never the effort and is empty before the first reply, so a new session before its first reply is refused until one reply has run the status line; exit code 2 would erase the prompt, so the hook never uses it; and whether the harness puts the refused text back into the input box depends on its version, so the engine repeats the text in the reason instead of relying on it. A session with no status line command can never pass a required-model message.

### `bf page set <name> <url>` / `bf page list [--json]`

A page the conductor publishes (the questions form, a gate page, the plan) is found again by a new session through the log. `page set` records where `<name>` was published; the name is the page's name without `.html` (`questions-<stage>`, the old `questions` still read, `gate-<gate id>`, `plan`, `run`, `index`, ...). It appends a `page.published` event with `name` and `url`; setting a name again replaces the earlier link. Only `https://` links are accepted. `page list` prints the latest link per name; `bf status --json` carries the same as `pages: [{name, url, at}]` and plain `bf status` prints one `page <name>: <url>` line each. A `bf next` directive that waits on the human for a gate (`decide-gate`) or for a worker's question (`answer-question`) includes `page_url` when a link for `gate-<gate id>` or `questions-<stage>` (an old `questions` link still counts) is recorded. Links are private: they live in the workspace's log and nowhere else, and the engine writes them into no code repository, no commit and no rendered page.

### `bf stuck [--dry-run]`

Parks every running unit with no event for `idle_minutes`, and lists all parked units. Units parked by review rounds are listed too. `bf next` runs the same check by itself.

### `bf doctor [--perf]`

`doctor` checks the key, the log chain, the guard table, the ignore line, ignored events and the plan. `--perf` times each class of command in the current project and prints medians and 99th percentiles, including `bf guard` as a real child process.

## The content hash

A receipt is bound to the content it ran on. The content hash is the **git tree-object hash of every file under the working copy's top folder that is tracked, staged, or untracked and not ignored, as the files are on disk when the command starts, leaving out the folders `factory/` and `.bf/`**. It is computed in a temporary copy of the index (`git add -A`, `git rm --cached` for the two folders, `git write-tree`), so the real index and the history are untouched. Files that `.gitignore` covers do not count; add build output to `.gitignore`. **Files an operating system writes by itself into a folder it shows never count either, whether untracked, changed or tracked: `.DS_Store`, the AppleDouble files whose names begin with `._`, and `Thumbs.db`, by name at any depth.** The same list leaves them out of the test for uncommitted changes (landing, checkpoint close, the sync) and out of the add before the landing commit, so they are never landed. The engine does this with git pathspec exclusions, so it writes no ignore file and no setting into a repository; a name that only contains one of these, such as `DS_Store.txt`, counts as any other file. The hash is taken before and after a command runs; if they differ, no receipt is written.

For a unit the working copy is `.bf/work/<U>`; for a checkpoint it is `.bf/work/<K>`; in the main checkout it is the checkout itself.

## The guard

`bf guard` is the hook that runs before every tool call. It reads the tool call on stdin and the project's guard table, `.bf/guard.json`, and checks the table's signature with the key in the state folder (the one extra small file it reads). It starts no process and calls no git. It judges a path by the place it leads to, as the next paragraph says. The table is numbered: every time the engine writes one it raises a counter kept next to the key, and the guard refuses a signed table whose number is below the counter, so an old copy put back loosens nothing.

**How links are judged.** Resolving a path with the system's canonical form is not enough, because it fails for a link whose target does not exist and then the link's own place is judged. The guard reads each symbolic link on a path itself, from the outermost folder inwards, an unresolved one included, and follows link after link, up to 40, taking a relative target from the folder that holds the link; the place it ends at is the place judged. A write, an edit or a shell write through a link is refused there when that place is protected or, in a unit's working copy, outside the unit's scope. In a unit's or a checkpoint's working copy the guard also judges the git plumbing that can turn a file into a link: `git update-index --cacheinfo` and `--index-info` refuse a link (mode 120000) and hold every path they write to the scope, and so does `git checkout-index` for the paths it writes (one that writes files it does not name is refused); `git hash-object -w`, which writes only the object store, passes. A request for files whose path is a link, or lies under a folder that is a link, in the working copy is refused before any review as a hard refusal, and so is a path with a letter whose case-folding gives an ASCII letter, such as the long s, the Kelvin sign, the dotted capital I, the sharp s (which upper-cases to SS) or a ligature such as fi, since it can open a file under another name on a case-insensitive disk. **The one form left unjudged** is a path object held in a variable in interpreter code (`p = Path('src/other.txt'); p.write_text('x')`): its path is named outside the call that writes, like a path built at run time.

**Which project, which table.** The guard looks for the project from the payload's `cwd`, from the file a write tool names and from the absolute paths a shell command names. When the hook command carries `--root <dir>` (or `$BF_ROOT` is set) that folder is the project and the only one looked at, so a `factory/` folder further up cannot take its place; the harness should always pass `--root "$CLAUDE_PROJECT_DIR"`. The **outermost** folder above each of them that has a `.bf/guard.json` or a `factory/` folder is the project, so a table planted deeper (inside a working copy, for example) is ignored. A project with a `factory/` folder whose table is missing, empty, not signed, signed wrongly or not its own **denies** every call, and says why; only a folder with neither is "not a factory" and left alone.

Configure it in the project's `.claude/settings.json` (the matcher must include the read tools):

```json
{
  "hooks": {
    "PreToolUse": [{ "matcher": "Write|Edit|MultiEdit|NotebookEdit|Bash|Read|Grep|Glob", "hooks": [{ "type": "command", "command": "bf guard" }] }],
    "UserPromptSubmit": [{ "hooks": [{ "type": "command", "command": "bf human-turn" }] }]
  }
}
```

**Input** (Claude Code's `PreToolUse` payload; only these fields are read):

```json
{ "tool_name": "Write", "tool_input": { "file_path": "/abs/path/factory/policy.toml" }, "cwd": "/abs/path" }
```

**Output** (always exit code 0). A call the table forbids:

```json
{ "hookSpecificOutput": { "hookEventName": "PreToolUse", "permissionDecision": "deny",
  "permissionDecisionReason": "refused: write factory/policy.toml\nbecause: ...\ndo this:\n  1. ...\nit worked when: ...\n" } }
```

A call it does not forbid prints `{}`: the guard **abstains**, so the harness's own permission prompts stay on. An explicit `allow` is printed only when the policy asks for it (`[guard] allow = "allow"`), because Claude Code runs an allowed call without asking.

**What the table holds** (signed, rewritten by every state-changing command): the project root; the protected paths (`factory/`, `.bf/`, `.claude/settings.json`, `.claude/settings.local.json`, the installed panel folder `.claude/skills/factory-panel/`, the git hooks and config and the policy's `protected_extra`); the state folder; the commands a worker and a verifier may run; and one entry per active unit and per checkpoint with its working copy path and file scope.

**What it decides:**

- `Write`, `Edit`, `MultiEdit`, `NotebookEdit`: denied on protected paths (after resolving `.`, `..`, absolute paths and symlinks) and in the state folder; inside a unit's working copy, denied outside the unit's `files`; denied in a checkpoint's working copy; denied outside its own working copy for a session that works in a unit's. Open to the conductor: `.bf/drafts/` and `factory/idea.md`.
- `Read`, `Grep`, `Glob`: the state folder and its parent folder are denied.
- `Bash`: the command line is parsed the way a shell reads it (quotes and backslashes removed: `g"it" push`, `b\f human-turn`; `$( )`, backticks, `sh -c` strings, `eval`, the command string of `trap`, a script read by `source` or `.` from standard input or a process substitution, and a script fed to a shell by a heredoc, a pipe or a process substitution (`bash <(echo '...')`) read the same way), and every rule below works on the parsed command: the programs, their arguments, the redirects, and the working directory after each `cd`, each resolved to a path. No rule asks whether a word such as `factory` occurs in the text. The body of a heredoc and the content of quoted strings are data and are not scanned. Then:
  - **The engine is found only where a shell would run it.** The guard reads the command line the way a shell does (quotes, `$( )`, backticks, heredocs, `&&`, `||`, `;`, `|`, a newline) and treats `bf` as a call only in command position: the first word of a simple command, after leading `VAR=value` assignments and the wrappers `env`, `command`, `exec`, `time`, `nohup`, `xargs`, `sudo`, and the string argument of `sh -c`, `bash -c`, `zsh -c` and `eval`, read the same way. The word `bf` as an argument of another program (`cargo test -p bf`, `ls crates/bf`), in quotes that are data for another program (a `grep` or `sed` pattern, `echo` text), in a comment, or in the body of a heredoc that feeds a program that is not a shell is not a call, and the same goes for `human-turn` appearing as data. In `bf evidence run <check> ... -- <command>` the part after `--` is a command line of its own, read by the same rule. A real call is judged as before: **`bf` must be called plainly** (a subcommand that is not a literal word from the list, `bf $(echo human)-turn`, `bf ${x}`, `bf "$(printf ...)"`, is denied; so is a `bf` reached through `eval`, `sh -c`, `bash -c`, `env`, `xargs`, `command`, `exec`, a backtick or `$(`), `bf human-turn` is denied, `$B human-turn` with a program built at run time is denied, and so is `sh -c` or `cargo` given an argument that spells `bf human-turn`, and so is code given to a language interpreter (`python3 -c`, `perl -e`, `node -e`, `awk`, or a script on standard input) that calls the command (`os.system('bf human-turn')`, `subprocess.run`, `system("bf human-turn")`). Code that only prints the phrase is not a call, inline or on standard input. Where the reading is unsure about a word that is not in command position, the word passes
  - **`bf human-turn` is refused wherever the engine's name is followed by that word**, in any argument position and behind any wrapper program, known or not (`timeout 5 bf human-turn`, `stdbuf -o0 bf human-turn`, `flock f bf human-turn`, `script -q /dev/null bf human-turn`, `find . -exec bf human-turn \;`, a variable that holds the engine's name). The one exception is a program that only prints or searches text (`echo`, `printf`, `grep`, `cat`, `ls`, `git`, `sed`, ...), whose arguments are data. The wrappers the parse knows, and finds the command behind, are `env`, `command`, `exec`, `time`, `nohup`, `nice`, `sudo`, `doas`, `timeout`, `stdbuf`, `flock`, `setsid`, `ionice`, `chrt`, `taskset`, `script`, `unbuffer`, `caffeinate`, `watch`, `xargs`. A command after `find -exec|-execdir|-ok|-okdir` is a command of its own and is judged by every rule here, and so is code piped or fed with `<<<` into a shell (`echo '...' | sh`, `printf ... | bash`), read as a command line;
  - a command word or redirect target that is the state folder, its parent folder or its project id, or that expands the variables that locate it (`$BF_STATE_HOME`, `$XDG_STATE_HOME`), is denied, and so is any word that resolves into it. The standard input of a `bf` command is never read for this;
  - **where a command would write, delete or run decides, never what its text says.** The guard resolves each of these against the working directory in force at that command (a `cd` changes it for the commands after it in the same shell; the `cd` inside `( )` is taken to hold afterwards, which can only refuse more) and denies it when it lands in `factory/`, `.bf/` (except `.bf/work/`, `.bf/drafts/` and `.bf/pages/`), the hook settings, the git folder of every registered code repository (its hooks, its config and the rest of its `.git`, for a repository inside the workspace and for one beside it alike, from every folder the command runs in), or the state folder (the whole protected list of the guard table). Reading there is not stopped (`cat <repo>/.git/config`, `ls <repo>/.git/hooks`, `cp <repo>/.git/config /tmp/x`), nor is a git command run on the repository (`git -C <repo> log`); a refusal of a write there names the resolved path. Inside a unit's own working copy the unit's file scope also governs each resolved write target, as it does for the write tools. The targets are: the target of a redirect (`>`, `>>`, `>|`, `&>`; `/dev/*` is skipped); the path arguments of `rm`, `tee`, `chmod`, `chown`, `truncate`, `touch`, `mkdir`, `rmdir`, `unlink`, `shred`, `patch`, `dd of=` (a word that is not a path is not one: the mode of `chmod` and the owner of `chown`, the value of `truncate -s|-r`, `mkdir -m`, `touch -t|-d|-r`, and the template of `mktemp -p <folder>`, which is judged as that folder), the sources and the destination of `mv`, and the destination of `cp`, `ln`, `install`, `rsync` (**when the destination is a folder** (it ends with a slash or a dot, it is given with `-t` or `--target-directory`, several sources are given, or it is a folder on disk, unless `-T` or `ln -n` says it is the thing itself), each source is judged where it lands: `cp x .claude/` is a write of `.claude/x`, and `cp /tmp/hello.txt src/` is a write of `src/hello.txt`, held to the file scope; a source that stands for its contents (a trailing slash, `.`, a variable, a pattern, input `xargs` hands over) lands as `<folder>/*`), the files of `sed -i` and `perl -i` (not the script), the starting points of `find -delete` (read after its leading options `-H`, `-L`, `-P`, `-D <x>`, `-O<n>`; **a `find` with a `-name` or `-iname` filter and no `-o` or group deletes what the filter matches, not its starting point**, so its targets are `<start>/<name>` (`find . -name '*.pyc' -delete` is a delete of `./*.pyc`), and from the main checkout the protected places below the starting point are also walked on disk: the command is refused when a protected file or folder can be one of the matches, whether it deletes or its `-exec` command writes (`find . -name '*.toml' -delete` and `find . -name '*.toml' -exec rm {} +` are refused because the records are `*.toml`; `find . -name '.DS_Store' -delete` passes). In a unit's working copy the root `.` of the copy is a folder like any other: a delete of it, `rm -rf .`, `find . -delete` or `git rm -r .`, is refused for the files it holds outside the scope. The command after `-exec` is judged by itself, with `{}` read as what the `find` matches (the starting point, or the starting point with the name filter), so `find factory -exec grep -l x {} \;` only reads; but when the command after `-exec`, read through a wrapper such as `env`, `nice` or `timeout`, is a shell or an interpreter that is given `{}` as an argument, the starting points stay write targets, since the inner code reaches them as `$1`, `$@` or `argv`; with a filter that is not so: the inner code is read with `{}` as the matches, and an interpreter that only reads them (`find src -name '*.py' -exec python3 -m py_compile {} \;`) passes; handed code that can write (a call such as `os.remove` or `unlink`, a write flag such as `O_WRONLY`, a redirect, or `rm`, `mv`, `cp`, `tee` and the like in a shell string) is a delete of the matches: from the main checkout the protected places below the starting point are walked, and in a unit's working copy `<start>/<name>` is held to the scope. **Known gap of the scope rule:** a name filter is judged at the top of its starting folder, so `find src -name hello.txt -delete` is read as a delete of `src/hello.txt` and passes when that file is in the scope, although `find` also reaches `src/sub/hello.txt`; the landing step refuses a branch that changes files outside the unit's list), the file of `find -fprint`, the paths of `git checkout|restore|rm|mv|clean` (not `git restore --staged` without `--worktree`, nor `git rm --cached`, which touch only the index), the output of `curl -o|-O` and `wget`; the output file of `sort -o`, the second file of `uniq` and `xxd`, the output option of `base64`, `openssl` and `gpg`, the archive of `zip`; the files the compressors rewrite (`gzip`, `bzip2`, `xz`, `zstd`, `gunzip` and the like, unless `-c`, `-t` or `-l` says nothing is written); the prefix `split` writes (`x` in the working directory when none is given); the files the line editors open (`ed`, `ex`, `vi`, `vim`, `nano`); `mktemp`, `mkfifo` and `sponge`; and the folder an archive is unpacked into by `tar x` and `unzip` (the working directory unless `-C` or `-d` says otherwise) with each member named, and the archive `tar c` writes; and the program or script that would be run (`./factory/x.sh`, `bash factory/x.sh`, `python3 .bf/x.py`, `source factory/x.sh`). Reading (`cat`, `ls`, `grep`, `sed -n`, `git status|diff|log|add`, ...) is not stopped, and neither is writing a path that lies elsewhere. A redirect, or a command that writes, whose path or folder is built at run time (`> "$X"`, `cd "$D" && echo x > a`) cannot be resolved: it is denied when the folder it is relative to is unknown or when the written text still holds a protected folder name as a path segment, and passes otherwise. A target that can be read further is read further, and is **refused when it could land in a protected place**: a variable assigned in the same command line (`D=factory; echo x > $D/p`) is read with its value; a brace (`{factory,tmp}/p`) is read as each of its alternatives; a glob (`fact*/p`, `./f?ctory`, `rm -rf *` in a folder that holds a protected one) and a command substitution (`$(echo factory)/p`) are read as a pattern of path segments, matched against every protected place, and a substitution at the start of a path may also stand for an absolute path (`$(pwd)/factory/p`). A word that is only a command substitution (`> $(mktemp)`) is an unknown path and passes. **A path that starts with a variable the command line does not assign (`> $OUT`, `> $UNKNOWN/policy.toml`, `> "$TMPDIR/out.txt"`) is refused:** the environment's value could be any path, a protected one included, and the agent can set it. The same variable in a folder position later in the path (`./$X/p`, `src/../$X/p`, `a$X/p`) is refused too. A last segment that is nothing but a variable (`./$OUT`, `src/$OUT`, `src/${OUT}`) is refused too, since its value can hold slashes or `..`. A positional parameter (`$1`, `$@`, `$*`) counts as a variable the line does not assign, even after `set -- <path>`, and is refused the same way. Inside a `sh -c` string the words after the string are its `$0`, `$1` and `$@`, and a write through them is judged as the paths they stand for (`sh -c 'rm -f $1' _ factory/policy.toml` is refused); a string that runs `set --` itself keeps them as variables the line does not assign. In a script fed to a shell (a heredoc, a pipe or a process substitution) `$0`, `$1` and `$@` are the words from the script operand on (`<(..)`, `/dev/stdin`, `-`), or the words after `-s`, and are judged the same way (`echo 'rm -f $1' | sh /dev/stdin factory/policy.toml` is refused). Not judged: a variable mixed into literal text in the last segment after known folders (`src/out-$N.txt`). (Position on the temporary folder variable: it is no exception. Write the path out, such as `/tmp/out.txt`, or assign the variable in the same line.) A pattern whose literal parts cannot meet a protected place (`/tmp/out-*`, `target/*.o`) passes. The folder before a pattern's first wildcard is still judged against the working copy, so a pattern that starts outside it is refused from a unit's working copy. A variable assigned more than once in the line is judged under every value it is given, so a later reassignment hides nothing. The values of a loop variable (`for d in a b`), of a variable set by `read` from a heredoc, a here string or `echo` and `printf` piped in, and the default of `${D:-value}`, `${D-value}`, `${D:=value}` are read the same way. A writer started through `xargs` is judged with its input added to its arguments when `echo`, `printf` or a heredoc gives the input, and is refused when the input is unknown and the writer deletes or edits in place (`find . | xargs rm`, `xargs sed -i`, `xargs truncate`, `xargs mv`). An `xargs -a FILE` or `--arg-file=FILE` reads its input from that file, so the input is unknown. With unknown input a writer is also refused when that input becomes its write target: the destination of `cp`, `ln`, `install` or `rsync` without `-t`, a compressor without `-c`, `-t` or `-l`, or the `-I` replacement string in a write-target argument. The same holds for a variable set by `read` from input the guard cannot see (`find factory | while read f; do cp /tmp/x "$f"; done`); there the refusal says the program would write the files the variable names. `sed -i ''` (an empty suffix word) is read with its files. In a checkpoint's working copy during an open sync a shell write is held to the files the sync allows, as the write tools are. Code for an interpreter that holds a relative path that starts in a protected folder is not refused for the path: a file a text tool or a script only reads (`awk 'NR<3' <a record>`, `python3 script.py <the records folder>`) and a string that is only data are not writes. Code that opens such a path for writing is a write like any other (see below), and so are `sed -i`, `perl -i` and `ruby -i` with the file named. A `print > "path"` of an awk program is read the same way. **Making a folder** (`mkdir`, `install -d`, `os.makedirs('a')`) passes in a unit's working copy when the folder leads to a path the unit may write (the directory part of a file entry, or the literal prefix of a pattern); removing a folder, and making one that leads to no entry of the scope, stays refused. **A target that holds a protected place** is refused like a target inside it: `rm`, `rmdir`, `unlink`, `shred`, `chmod`, `chown`, `find -delete`, the sources of `mv`, the name of an `ln` and the paths of `git checkout|restore|rm|mv|clean` whose path is a folder above `factory/`, `.bf/`, the hook settings or the git hooks (`rm -rf .claude`, `mv .git .git2`, `rm -rf .`, `git checkout .`, `ln -sfn /tmp/x .claude`). A recursive `cp` or an `rsync` into such a folder is refused when its source is a protected folder's name or the whole contents of a folder, a source whose last segment is a pattern included (`cp -R /tmp/x/factory .`, `cp -R /tmp/x/. .`, `cp -R /tmp/x/* .`, `rsync -a /tmp/x/ ./`). An archive unpacked with no member named into a folder that holds a protected place (`tar xf a.tar -C .claude`, `unzip a.zip -d .claude`) is refused too, and `cp -T` and `cp -rT` into such a folder are read as the whole contents of the source; `chmod` that only takes permissions away (`chmod -R go-w .`) is not read as a target that covers. A recursive `chmod`, `chown` or `chgrp` of the root of a unit's working copy (`chmod -R 000 .`) is refused like a delete of it, except a `chmod` that only takes permissions away; the same command on a folder or file in the scope passes. Not judged: unpacking an archive (`tar x`, `unzip`) with no `-C` or `-d` into the main checkout's root, which can land in a protected folder; the agent that names the members, or unpacks elsewhere, is not stopped either way. The sources of `mv` are all read, with or without `-t`. In a unit's working copy a pattern is held to the file scope as written: it passes only when the pattern itself matches an entry of the scope (`src/*.rs` against `src/**`), and is refused otherwise. Unpacking (`tar x`, `unzip`) into a unit's or a checkpoint's working copy with no member named is refused, because what lands is the archive's own and the scope cannot be applied to it; name the members, or unpack outside the project (`-C /tmp/x`, `-d /tmp/x`) and copy what is needed. Known gap of the scope rule: downloading (`wget`, `curl -O`) into the working copy's root names no member, so the scope is not applied to what lands there; the protected places are still judged. A symbolic or hard link (`ln`) is judged on every path it is given, the one it points at included (a relative target of a symbolic link is read from the folder the link is made in, so `ln -s ../src/a.rs build/a.rs` points at `src/a.rs`), so a link to a protected place cannot be made and written through. A folder reached by `cd fac*` is a pattern, and what is written relative to it is judged as a pattern. Code for an interpreter (inline, or on standard input) that opens a path given as a string literal for writing or deletes it (`open('a','w')`, `Path('a').write_text`, `writeFileSync('a')`, `os.remove('a')`, perl `open(F,'>a')`) is a write to that path: the protected places and a unit's file scope judge it like any other write, and a path it only reads, or names in text, is not stopped. An absolute path in such code is judged as a write only when the code writes in a way that is not a named literal (a mode flag such as `O_WRONLY`, `chmod`, a shell-out, a path held in a variable) or the path is mentioned other than to read it; a path whose every mention is read (`open('<abs>')`, `open('<abs>', 'rb')`, `readFileSync`, the source of `shutil.copy`) passes, so `shutil.copy('<root>/factory/records/R-1.toml', '/tmp/r1.toml')` passes and writes only the destination. **Shell rules that read raw text, by choice:** the guard has to read the text of code given to an interpreter (`code_may_write`, `written_literals`, `read_literals`, `made_literals`, `awk_written`, `code_calls_human_turn`, the path scan of the code, `ruby_file_delete`, `writes_without_literal`, `write_through_variable`, `mask_literal_deletes` and `literals_for_unnamed_writes`), because that code is not shell and has no parse here; it looks for path literals and calls, never for plain words. `ruby_file_delete` and `writes_without_literal` read the raw text because a delete through a file object or a variable names no path in the call, so the only way to judge it is to take every path literal of the code as written; `ruby_file_delete` skips quoted text. **The per-rule list** (R-54): matching raw text, by the reason above: the eleven interpreter-code rules just named, plus `handed_code_may_write` (its test whether a string holds a writer). Working on parsed words, redirects and the working directory: the redirect targets; the path arguments of the writers (`rm`, `tee`, `chmod`, `chown`, `truncate`, `touch`, `mkdir`, `rmdir`, `unlink`, `shred`, `patch`, `mkfifo`, `mktemp`, `sponge`, `dd of=`); `mv`; `cp`, `ln`, `install`, `rsync`; `sed -i`, `perl -i`, `ruby -i`; `find -delete`, `-fprint` and `-exec`; `git` (`checkout`, `restore`, `rm`, `mv`, `clean`, `switch`, `read-tree`, `reset`, and the refusals of `--git-dir`, `-c core.*`); `curl`, `wget`; the compressors; the line editors; `tar`, `unzip`; `sort -o`, `uniq`, `xxd`, `base64`, `openssl`, `gpg`, `zip`, `split`; the program or script that would be run; `xargs` input; `chmod -R` of the copy's root; the human-turn call by a parsed program; the variable, brace, glob and substitution expansion of every target. Every other shell rule works on the parsed words, redirects and working directory. A copy (`shutil.copyfile`, `copy2`, `copytree`, `copyFileSync`) writes only its destination, so its source is not judged as a write; a rename writes the destination and deletes the source, so both are judged, and so are `os.replace`, `shutil.move`, `shutil.copy` (destination only), `os.symlink`, `os.link`, `fs.cpSync`, `fs.symlinkSync`, the ruby `File.write`, `File.delete` and `FileUtils` calls, and a path object's `replace`, `move`, `symlink_to` and `open('w')`; a folder made through a path object (`Path('src').mkdir(parents=True)`) is a made folder.   - from a unit's working copy (a landed unit's old copy counts too) the only `bf` commands are `evidence run|verify|fail|unreachable|attach`, `report`, `record put finding`, `record get|list` and `status`; from a checkpoint's working copy the same without `report` and `record put`. `bf -C`, a `cd` out of the working copy, and a write whose target is elsewhere in the project are denied there.
- Every other tool is allowed (abstained).

**What a shell refusal says.** It names the resolved path and the part of the command that reached it (`the redirect `> ../../../factory/policy.toml` would write /project/factory/policy.toml`, `` `rm` with the argument `factory/records` ``, `the code given to `python3` (it holds the path ...)`, `the program ./factory/run.sh`), and its steps say what to do for that case: an engine command for a record, a path inside the working copy for a file of your own, the human for the policy. It never asks for the names of the folders to be kept out of the command.

**Every shell rule, and whether it matched raw text** (R-54). Each rule works on the parsed command; the two that still compare text say why.

| Rule | Reads | Raw text before | Now |
|---|---|---|---|
| `bf` called plainly, `bf human-turn` refused, worker and checkpoint lists of `bf` commands, `bf -C` | parsed command position | no (already parsed) | unchanged |
| `$B human-turn`, a program built at run time given the word `human-turn` | parsed words | no | unchanged |
| `sh -c` or `cargo` given an argument with the phrase `bf human-turn`; code for a language interpreter that calls it | the arguments, and the code on standard input, of the interpreter | yes, a phrase in a string | **kept, narrowed** (an interpreter's code is refused for a call such as `os.system('bf human-turn')`, never for the phrase alone, inline or on standard input): the phrase is one specific command that only the harness may run, a path cannot express it, and the body of a heredoc is not an argument and is not read |
| The engine's name followed by `human-turn` as separate words, behind a wrapper the parse does not know | the parsed words of each simple command (`find -exec` commands and code piped into a shell included) | no (new in U-28) | **kept as a word match inside the parsed command**: an unknown wrapper cannot be read, so the two words are what is left of the call; programs that only print or search text are exempt, and a quoted string is one word and is not read |
| A target with a glob, a brace, a substitution or a variable assigned in the line | the parsed word, expanded and matched as path segments against the protected places | no (new in U-28) | parsed and matched on segments, never on the text of the command |
| The writers that the old rule refused by naming (`sort -o`, the compressors, `split`, the line editors, `tar x`, `unzip`, `uniq`, `xxd` and other output files) | parsed arguments, resolved | yes (any command that named a protected path and was not a read) | parsed and resolved; the list of writers is in the rule above, and a program that is in none of the lists is what TH-18 leaves open |
| The state folder, its parent, its project id, `$BF_STATE_HOME`, `$XDG_STATE_HOME` | parsed words and redirect targets, then each word resolved from the working directory | yes, over the whole text with quotes stripped | **kept as a word match on a unique string** (an absolute path or an id that does not occur by chance, which can be glued into `--dir=...` or a glob where a path cannot be resolved); heredoc bodies and the standard input of `bf` are not read |
| `cd` or `pushd` out of a working copy | parsed `cd`, resolved | yes (split text) | parsed |
| Dangerous `git` subcommands, `--git-dir`, `-c core.*`, `git config` | parsed `git` words, with `-C` and the tracked working directory | yes (split text) | parsed |
| Protected paths named by anything that is not a read | resolved redirect targets, the path arguments of programs that write or delete, the program or script that would run | yes (every token of a segment; a heredoc body counted) | parsed and resolved; the rule of this unit |
| Text fed to an interpreter | path strings in its code, resolved | yes (the whole text) | path strings only; a protected path in code that cannot write is a read (U-44) |
| A copy, move, link, install or sync into a folder | the parsed destination and sources; whether the destination is a folder is read from disk | no (the folder was judged as the write, not the file that lands) | the file that lands is judged (U-44) |
| The mode, size, time and template words of `chmod`, `truncate`, `mkdir`, `touch`, `mktemp` | parsed arguments, the option's value skipped | no (every word that was not an option was a path) | not paths (U-44) |

| Writing under the transcript root | resolved write targets | yes | resolved |
| A working copy writes only inside itself | resolved write targets | yes (a `>` found in the text) | resolved |
| The folders whose table judges the call | absolute paths in parsed words, redirects and interpreter text | yes (raw absolute words) | parsed |

The `Read`, `Grep` and `Glob` rules are not shell rules: they judge the path the tool is given, and a `Grep` pattern that holds the state folder's path or a `Glob` pattern for another project's folder is compared as text because the tool's input is the pattern.

**Every shell rule of the guard, and whether it reads raw text (R-54).** All rules start from the parsed command (programs, arguments, redirects, working directory after each `cd`, heredoc input). The ones that still look at text, and why:

| Rule | Reads | Why it stays |
|---|---|---|
| a call of `bf`, its subcommand, `-C` | parsed words in command position | none left |
| `bf human-turn` behind a program built at run time, or behind an unknown wrapper | parsed words | none left |
| `cargo`, `sh`, `bash`, `zsh` given an argument that spells `bf human-turn` | parsed arguments, substring of one word | an argument of these programs is run as a command line; the substring is the only way to see it |
| code for an interpreter calls `bf human-turn` | raw code text (call words and the phrase) | code in another language cannot be parsed here; the rule asks for a call word, so printing the phrase passes |
| paths in interpreter code (absolute, home, `../`) and paths opened for writing (a relative path is judged only where the code writes it) | raw code text, as path strings only | the same; it never looks for bare words, and a path built at run time is a known gap |

| whether code that only reads an absolute path can still write by a means with no literal (`os.remove(f.name)`, `s.path`, a shell-out) | raw code text, as calls and attributes only | the same; `name` and `fileno` count as an attribute (`f.name`), `remove`, `run`, `call` and the like as a call, and `remove` on a list or set (`items.remove(x)`), a dict key (`d['name']`) and the `path` module do not |

| the state folder named in any word or redirect | parsed words, substring | deliberate: the key and the log head must not be named at all |
| redirect targets and the path arguments of writers, deleters and editors | parsed words, resolved to a path | none left |
| the `xargs`, `read`, loop-variable and `${D:-x}` readings | parsed words | none left |
| a makefile on standard input | heredoc text, read as shell lines | the recipe is the only place the command is |
| git subcommands | parsed words | none left |
| the program or script that would run | parsed first word or script argument | none left |

What is left open by this change, on purpose (TH-18, TH-19): a program that is not in the lists above and writes by its own means (a build script, `make`, a program given a protected path as an argument), a form of command the parse does not understand, and a script that builds a protected path at run time. They were never stopped by text matching either; the layer under the guard is the harness's own permission checks and sandbox (below).

Measured in this repository's tests, the guard takes about 2 ms per call as a separate process (design target: 30 ms median).

The engine also enforces the worker limits itself, without the hook: a command run from inside a working copy (by the process's real current directory, not by `-C`) is limited to the same list, and `bf next`, `bf brief`, gates, landing and planning are refused there.

## What the engine does not stop

The guard and the checks stop mistakes, drift and casual cheating, and make deliberate cheating visible. They do not make a determined agent honest. There are two cases.

**A worker with only the guarded tools (Write, Edit, Read, Grep, Glob, and Bash through the hook).** After the checks above it can no longer, in a few calls, record a human turn, approve a gate with the human's refusal, edit the policy or the check records unnoticed, add a unit to an approved plan, read the key by name, plant a program in a folder it was told about, or move the main branch without the engine saying so. What it can still do:

- **Hide a path.** The guard reads the parsed command and the path strings in an interpreter's code. A path built at run time (`'fac' + 'tory'` inside a script, a variable, a glob such as `fact*/`) or a script file that does the work (`sh src/x.sh`) is not seen. The sandbox around checks and git helps only where the engine starts the process; a worker's own Bash call is not sandboxed unless the harness does it.
- **Run its own code as a check.** A check runs the unit's code; that is the point of it. On macOS the engine runs it in a sandbox (no state folder, no network, no writes to `factory/` or other working copies); elsewhere it runs unsandboxed and the receipt says so. Either way the code can do what it likes inside its working copy and its temporary folder, and what a check proves rests on someone reading that code.
- **Plant a program where checks look.** The folders on the check PATH are not watched for change. A program replaced in place is noted in the receipt of the next run (see `bf evidence run`), only for the first word of a check's command.
- **Use a token as the conductor.** A token tells roles apart and does not keep the conductor out: the conductor reads every token from `bf next`, so it could settle a check, attach an outcome, file a review or report in a role's name. The engine cannot stop this (a known and accepted limit). The conductor's instructions forbid it, and that rule rests on the conductor alone; the only report it files for a worker is the relay under a budget cap.
- **Take the reviewer's token.** The token only says which role is reporting. A worker that runs `bf next` from a script before the conductor does can read the reviewer's token; the engine refuses `bf next` from a working copy, and the rest is left to Claude Code's own permission checks (below).
- **Move main, then be noticed.** The engine sees a move of the main branch the next time it reads, and refuses to land, close or call the ledger closed until the human accepts the position. It does not stop the move: only a host's branch protection does.

### What Claude Code's own permission checks are relied on for

The engine is there so that nothing is forgotten: every ID linked, every unit reviewed, every gate decided in order, every decision shown with the words behind it. It is not a box for an agent that means to hide something. Hiding takes a script or an interpreter, and that is the layer Claude Code's own permission prompts (and, under auto mode, its own checks of deceptive actions) see, because they see the call as it runs. These routes are therefore left to that layer, and the engine adds no text matching for them, because every such rule can refuse an ordinary command:

- a script the agent writes in a file it may write and then runs, reaching the state folder, the key or a transcript by a path built at run time;
- a Bash call that builds a protected path, a `bf` subcommand or an environment variable name from pieces (`'fac' + 'tory'`, `B=bf; $B ...`, `base64 -d | sh`);
- an interpreter (`python3 -c`, `node -e`, `perl -e`) that writes to `factory/` or the policy by a relative path, or by a path it builds at run time, without a shell redirect (an absolute path in code that opens it for writing is refused; code that only reads it passes, by an absolute path as by a relative one);
- a worker that reaches `bf next` from a script before the conductor does and so is offered the reviewer's token; a builder that reviews itself this way;
- a worker that starts `sandbox-exec` with a permissive profile of its own, so that a check runs unsandboxed (the receipt says `sandbox = "none"`);
- a builder that reports `fixed` without changing anything (every open finding is then marked fixed), or attaches any file to an agent-run check;
- one human message used for a gate other than the one it was meant for, and the same payload piped to `bf human-turn` twice;
- the Write tool writing outside the project from a unit's working copy;
- a flaky check re-run until it passes; a check that depends on a file the content hash does not see;
- `bf init` run with another state folder, which re-signs the guard table with a new key.

Where a person wants more than that, the harness's own sandbox for worker sessions, with the state folder, `factory/`, `.bf/`, `.git/` and the transcripts denied, is the layer that does it (below).

**An agent with an unrestricted shell under the same user account.** It can read the state folder (`~/.local/state/blackfactory/<id>/`): with the key it can seal receipts, chain log lines, sign a guard table, rewrite the log and its head together, and hand itself role tokens. It can write anywhere the user can, including the policy and the transcripts. Nothing in this engine stops that. Real separation needs:

- **the harness's sandbox**, so that worker sessions cannot read or write the state folder, `factory/`, `.bf/`, the transcripts and other working copies at all (layer 1 of D-3; not built here); and
- **a host identity the agent does not hold**: a pull request on the host that only the human merges, with required checks that re-verify every receipt.

What each protection gives, and what stays open:

| Protection | What remains |
|---|---|
| Key and head outside the project tree | Same-account shell can read them; forging a line needs the key, undoing a rollback needs the head |
| Signed guard table with a counter, outermost project, links followed to where they lead | A same-account agent can still write files by means the command text hides |
| Accepted policy in the state folder | A same-account agent can replace the copy and the head together |
| Role tokens | A script that asks for a token before the conductor does gets one; the conductor's second request voids it with a note; a leaked token is a role |
| The quote and the whole message stored with every decision, with a caution when a word points the other way | The engine does not understand the sentence; the conductor's reading is the decision, and the human can see it |
| Hook payload checks; the transcript noted beside each turn | The transcripts are the harness's own files and are not a gate; a program that can feed the hook can make a human turn |
| Clean environment, sandbox and PATH check | Not complete: see above |
| Main-branch watch | It notices after the fact, and only work that should not be there |
| Program hashes at the plan gate | A note in the receipt, not a refusal; only the first word of a check's command |
| Cost on every report | The number is still the conductor's word |
| Frozen records and receipt-to-check binding | A same-account agent could edit records and the log together |

## Scans, presets and legal acknowledgements

**`bf scan secrets` and `bf scan licences`** (`licenses` too) run where their check runs. Two ways, with the same receipt: from inside the working copy run `bf scan secrets` (or `licences`) itself, or run the check the usual way, `bf evidence run <check> -- bf scan secrets` (the verifier's normal flow, no change of any role file). A command check whose command is exactly `bf scan secrets|licences|licenses` is run by the engine in its own process, in the working copy `bf evidence run` is run for: the sandbox hides the sealing key from the command a worker passes, so the scan could not write its own receipt there, but the engine can, and the scan's tool still runs sandboxed with no network. The receipt is for exactly that check at the content the scan read. A scan hashes the content before its tool starts and again after it ends; if the files changed in between (a worker writing while the scan runs, or a report file the tool writes that git does not ignore) it writes no receipt and refuses with the four parts. The command is allowed in a working copy, and the refusal of any other command in a working copy names this form. Example: `cd .bf/work/K-1 && bf scan secrets && bf scan licences`. From the project folder a scan covers the main checkout, so its receipt counts only at that content.

**`--check <ID>`** names the check record a scan proves. It is accepted only for a command check whose command is exactly `bf scan <that sub>`; a scan named for any other check (a test command, the other scan, a record that does not exist) is refused with the four parts and writes no receipt. Without `--check` the engine finds the record by its command.

**`bf uiux coverage <check>`** prints the state of every step of a UI/UX verification check: each journey step, each screen state and the accessibility result, as met, failed, unreachable or missing at the content as it is now. It reads only; the verifier settles the steps with `bf evidence attach`.

**`bf preset list|fill`**: `bf preset fill <kind> <language> <values-file> [<out-file>]` prints the draft, or writes it under `.bf/drafts/` of the project folder and nowhere else. A bare file name is placed there; a path must resolve (links followed) to a place inside `.bf/drafts/`, so a record, the hook settings, `factory/` or `.claude/` is never written and the command refuses it with the four parts.

**Legal acknowledgement.** The human's acknowledgement of a marked legal finding is bound to what they read: the closing question stores a hash of the finding's title, text, severity, where, action, market and links, and of its risk, markets, research mark and sources. A change of any of these after the question was asked (by a plain `bf record put legal --replace` or by filing it again) makes the finding unacknowledged: it holds the close of the checkpoint and of the run until `bf legal questions` asks again and the human answers again. A change of the outcome alone does not.

## Git: the `git` program, not a library


The engine runs the `git` program for every git read and write. It does not use a Rust git library such as `gix`, and its dependencies contain none. It makes one to three git calls per command that needs git (the content hash is three calls; creating or merging a working copy is one to three), and none at all from `bf guard`, `bf human-turn`, `bf next` (before a checkpoint is ready), queries and state changes of records. The reasons: a library would add many crates and a long build for the few operations needed here, and the operations that matter (a tree hash of the files on disk including untracked ones, worktrees, merges) are the ones where the `git` program is the reference behaviour. The measured times of every class of command are in the test output of the timing tests, which are left out of the default suite (`cargo nextest run --package=bf`) and run in the extended suite (`cargo nextest run --package=bf --profile extended`) at a checkpoint on a quiet machine. The test files are one program, so a check that selects the tests of one file names it as a test path: `cargo test --package=bf <file>::` or `cargo nextest run --package=bf -E 'test(<file>::)'`; the old form `--test <file>` finds no target.

## Testing aids

`BF_CRASH_AT=<point>` makes `bf` exit with code 137 at a named point, to test resuming a killed run. The points are `unit-start-after-git` and `land-after-merge`. It does nothing else.
